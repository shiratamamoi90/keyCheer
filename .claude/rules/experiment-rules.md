# 探索のルール(非決定的部分)

## いつ使うか

出力が指標でしか評価できないとき。KeyCheer では:応援メッセージの品質(らしさ/面白さ/多様性)、生成レイテンシ、sd.cpp キャラ画像の品質、プリキャッシュのヒット率など。
文言や画像の「良さ」を spec/test で縛ろうとしない(クラッシュしない・契約を満たす・予算内、という決定的部分だけ tests/ で縛る)。

## 単位:experiments/NNNN-xxx/

- `hypothesis.md`:仮説 / 測り方(指標・試行数・シード) / 中止条件。
- `config.yaml`:変更したパラメータ。
- `result.md`:指標の実測値 + 考察。**シードと依存を固定した再現可能な条件でのみ記録**。

## 規律

- 1実験 = 1つの変数変更。何を変えたら指標がどう動いたかを追えること。
- baseline を最初に作り、すべての実験は「baseline をどれだけ上回ったか」で測る。
- 失敗実験も result を残す(なぜダメだったかが次の仮説になる)。

## hypothesis.md テンプレ

```markdown
# 仮説

<X を変えると指標 Y がこう動くはず。例:プロンプトに速度ゾーンを入れると文言の状況適合度が上がる>

## 測り方

<評価データ(状況サンプル)、試行数、モデル/シード固定、見る指標(人手スコア/多様性/レイテンシ)>

## 中止条件

<レイテンシ予算超過 / 明確な品質悪化なら中止して baseline(定型文 or 現行プロンプト)に戻す>
```
