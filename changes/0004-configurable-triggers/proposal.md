# 提案 0004: トリガー条件の設定可能化と通常応援デフォルトの緩和

## なぜ

応援が出る頻度は体験の中核だが、現在は通常応援間隔(100 キー)もアクティブ判定(60 秒)も **コードに固定**されており、ユーザーごとの「ちょうど良さ」を吸収できない。100 キー間隔は実利用で「なかなか応援が来ない」と感じやすいため、デフォルトを **50** に下げると同時に、キー数と秒数を **UI から変更可能** にする。

## 方針

- `triggers.regular` の **既定値を 100 → 50** に変更。
- 設定 UI から次を変更可能にする:
  - 通常応援の間隔(キー数)
  - マイルストーン一覧(キー数の配列、追加/削除/編集)
  - アクティブ判定の秒数
- 変更は **即時反映**(再起動不要)。
- 値域はバリデーションする(不正値は拒否、設定 JSON 直接編集にも防御)。
- **速度ゾーン閾値(slow/normal/fast = 100/250)はトリガー条件ではない**ため、本変更の対象外。
- **KPM 算出窓(直近 1 分)はアクティブ閾値とは独立**で固定する(後述「要確認」のとおり、推奨)。

## 影響範囲

- MODIFIED:
  - `specs/cheer-trigger.md`: 通常応援間隔・マイルストーンが設定値であることを明示
  - `specs/key-counter.md`: アクティブ判定の秒数が設定値であることを明示(KPM 窓は別)
  - `specs/data-model.md`: `triggers.regular` の既定 100 → 50、`triggers.activeThresholdSec` を追加、バリデーションシナリオを追加
  - 設定 UI(Phase 1 MVP のスコープに含める)
- ADDED:
  - engine 側の `triggerConfig` 型・既定値・バリデーション関数
- 変えない(不変条件として維持):
  - 速度ゾーン閾値・分類ロジック(別軸)
  - プライバシー方針(キー種類のみカウント・発動経路の外部依存ゼロ)
  - cheerHistory のフィールド構造

## 種別判定

**決定的**(同じ設定 + 同じ押下時刻列 → 同じ発動)。仕様ループで進める。
※「ユーザーがこの値域でちょうど良さを感じるか」は非決定的だが、本 change はその**選択を可能にする枠組み**を縛るだけ。良し悪しは β 利用で測る(experiments 対象外)。

## 確定事項(承認済み)

- **KPM 窓 = 60 秒固定、`activeThresholdSec` とは独立**(KPM は「分」表記の意味を保つ)
- **既存 `triggers.regular = 100` はアップデート時に 50 にリセット**(新既定を反映。マイグレーション通知を起動時に出す)
- **値域**
  - 通常応援間隔: `1 ≦ N ≦ 10000`
  - アクティブ秒数: `5 ≦ s ≦ 600`(10 分)
  - マイルストーン最大個数: `20`
- **マイルストーン空配列は許容**(`milestone` 機能 OFF として扱う)
