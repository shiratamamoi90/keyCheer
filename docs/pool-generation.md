# 要件: プール・wav の生成と永続化、生成物での応援発動

キャラのプロフィールからローカルプロバイダー(Ollama / VOICEVOX)でメッセージプールと
wav を生成して永続化し、起動時に読み込んで応援発動に使う。

生成された文言の質、生成にかかる時間の良し悪しは仕様化しない(→ experiments/)。
ここで縛るのは**永続化の契約・起動時の紐付け・中断と再開・失敗時の挙動**。

保存パスと `characterId` のデータ契約は `docs/data-model.md`、
プロバイダー呼び出しの契約は `docs/integrations.md` を参照。

## 確定事項(2026-07-26)

| 項目 | 確定 |
| --- | --- |
| `characterId` | 保存時に採番する不変 ID(名前に依存しない) |
| 生成の起動導線 | 保存とは別の「生成」ボタン(保存だけして後で生成できる) |
| 生成中にウィンドウを閉じた場合 | 生成は継続する(閉じても中断しない) |
| wav が全滅した場合 | プールが揃っていれば作成完了(テキストのみで応援) |
| 既にプールがある状態で再生成 | 全バケットを作り直し、古い wav は削除する(再開か作り直しかの判定は S0038_01〜06) |
| `system` 設定の UI | 出さない(既定値のみ。設定 UI は別 change) |

### S0020_01 ローカル生成でプールと wav が揃う

- GIVEN プロフィールが保存済みで、Ollama と VOICEVOX が起動している
- WHEN 生成を開始する
- THEN 24 バケットのプールを `pool.json` に保存し、各文の wav を `voices/` に保存する

### S0020_02 生成の進捗が通知される

- GIVEN 生成を開始した
- WHEN テキスト生成 / 音声合成が進む
- THEN 現在の工程(text / voice)と進捗(完了数 / 総数)が UI へ届く
- ※ 更新頻度・表示デザインは仕様化しない

### S0020_03 Ollama 未起動で生成を開始した [異常系]

- GIVEN Ollama が起動していない
- WHEN 生成を開始する
- THEN クラッシュせず生成は失敗として終わる。音声合成には進まない。
  プールは使えるものにならず、応援は baseline 定型文のまま継続する

### S0020_04 VOICEVOX 未起動で音声だけ失敗した [異常系]

- GIVEN プールは生成できたが VOICEVOX が起動していない
- WHEN 音声合成に進む
- THEN wav は 1 本も保存されないが `pool.json` は保存され、
  応援は**プールの文言 + 音声なし**で成立する

### S0020_05 音声の部分失敗を許容する [境界]

- GIVEN 一部の文だけ wav 合成に失敗した
- WHEN 生成を終える
- THEN 失敗した文は wav 欠損として扱い、生成自体は完了とする
  (発動時はその文だけテキストのみ)

### S0020_06 生成を中断して再開する

- GIVEN 生成が途中まで進んでいる
- WHEN ユーザーが中断する
- THEN それまでの結果は `completion` に未完了を含む形で保存され、
  再開すると `complete` のバケットは作り直さず未完了分だけを続行する

### S0020_07 生成中に再度生成を開始できない [境界]

- GIVEN 生成が実行中
- WHEN もう一度生成を開始しようとする
- THEN 二重に走らせず、実行中である旨を返す

### S0020_08 起動時にプールを読み込んで応援に使う

- GIVEN 生成済みのプールと wav が保存されている
- WHEN アプリを起動して応援が発動する
- THEN baseline 定型文ではなく**プールの文言**が表示され、
  対応する wav が存在すれば `wavPath` が非 null になる

### S0020_09 キャラ未作成なら baseline で応援する

- GIVEN キャラが未作成、またはプールが無い
- WHEN 応援が発動する
- THEN baseline 定型文を表示し `wavPath` は null

### S0020_10 生成直後は再起動なしで応援に反映される

- GIVEN 生成が完了し、そのキャラクターが使用中になった(論点 0032。S0032_19 / S0032_21)
- WHEN 次の応援が発動する
- THEN 再起動しなくても新しいプールが使われる

## 要件: 複数のキャラクターがあるときの生成(論点 0032)

生成は選んだキャラクターに対して行い、完了したらそのキャラクターを使用中にするかを設定で選べる。

### S0032_18 生成は選んだキャラクターに対して行う

- GIVEN キャラクター C と D が保存されている
- WHEN C を選んで生成を開始する
- THEN C のプロフィールでプールと wav を作り、`characters/{C の id}/` に保存する。
  D のプール・wav・`generatedBy` は**変化しない**

### S0032_19 生成が完了したらそのキャラクターを使用中にする

- GIVEN `generation.shouldActivateOnComplete = true`(既定)、使用中は D
- WHEN キャラクター C の生成が完了する
- THEN 使用中を C にする。次の応援から再起動なしで C のプールを使う

### S0032_20 自動で使用中にしない設定なら使用中を変えない [否定]

- GIVEN `generation.shouldActivateOnComplete = false`、使用中は D
- WHEN キャラクター C の生成が完了する
- THEN `activeCharacterId` は D のまま**変化しない**

### S0032_21 自動で使用中にしない設定でも、使用中が無ければ使用中にする [境界]

- GIVEN `generation.shouldActivateOnComplete = false`、使用中のキャラクターが無い(S0032_15 の状態)
- WHEN キャラクター C の生成が完了する
- THEN 使用中を C にする

### S0032_22 生成後にプロフィールを変えたことが分かる

- GIVEN キャラクター C のプールが `generatedProfile` を持ち、その後 C の名前・性格・話者のいずれかを変えた
- WHEN C の状態を判定する
- THEN 「生成後にプロフィールを変えた」と判定する。元の値に戻したら判定しない。
  判定してもプール・wav は消さず、応援にもそのまま使う

### S0032_23 生成時のプロフィールを持たないプールは「変えた」と判定しない [境界]

- GIVEN `generatedProfile` を持たない旧いプール
- WHEN C の状態を判定する
- THEN 「生成後にプロフィールを変えた」と判定しない(比べる元が無いので推測しない)

### S0032_32 中断・失敗した生成では使用中を変えない [否定]

- GIVEN `generation.shouldActivateOnComplete = true`、使用中は D
- WHEN キャラクター C の生成を中断する、または失敗する
- THEN `activeCharacterId` は D のまま**変化しない**

## 要件: 生成でキャラ画像も作る(論点 0036)

1 回の生成で **テキスト → 音声 → 画像** の順に作る。画像は 1 キャラ 3 枚(待機画像・`regular`・`milestone`)。
画像タグの要求とプロバイダーの契約は `docs/integrations.md`、保存先は `docs/data-model.md`「画像ファイル」。
画像の失敗・欠損は wav と同じく生成全体を失敗にしない(応援は画像なしでも成立する)。

### S0036_07 生成でプール・wav の後に画像 3 枚を保存する

- GIVEN プロフィールが保存済みで、テキスト・音声・画像のプロバイダーが使える
- WHEN 生成を開始する
- THEN プールと wav を保存したあと、`idle` / `regular` / `milestone` の 3 枚を `images/` に保存して生成を完了する

### S0036_08 進捗に画像の工程が含まれる

- GIVEN 生成を開始した
- WHEN 画像の工程に進む
- THEN 現在の工程が image として、進捗(完了数 / 3)とともに UI へ届く(S0020_02 の工程に image が加わる)

### S0036_09 画像の一部が失敗しても生成は完了とする [境界]

- GIVEN プールは生成でき、画像 3 枚のうち 1 枚だけ作れなかった
- WHEN 生成を終える
- THEN 作れた画像を保存して生成は完了とする。欠けた画像は表示時に待機画像で代わる(`docs/popup.md` S0036_20)

### S0036_10 画像プロバイダーが使えなくても生成は完了とする [異常系]

- GIVEN プールは生成できたが、画像プロバイダーが使えない(sd.cpp のモデル重みが未取得 / 外部 API キーが無い / 通信できない)
- WHEN 画像の工程に進む
- THEN 画像は 1 枚も保存されないが生成は完了とし、応援は画像なしで成立する。エラーを表示する。
  **自動で別の画像プロバイダーに切り替えない**(S0016_06)。クラッシュしない

### S0036_11 テキストが失敗したら画像に進まない [異常系]

- GIVEN プールを生成できなかった(S0020_03)
- WHEN 生成が失敗として終わる
- THEN 画像タグの要求も画像の生成も行わない

### S0036_12 中断して再開すると、保存済みの画像は作り直さない

- GIVEN 画像の工程の途中で中断し、`idle` だけが保存されている
- WHEN 再開する
- THEN `regular` と `milestone` だけを作り、`idle` は作り直さない
  (`local-sdcpp` は下絵にする縮小前の待機画像が要る。残っていなければ 3 枚とも作り直す。`docs/integrations.md` S0046_17 / S0046_18)

### S0036_13 再生成で画像も作り直し、前の画像を残さない

- GIVEN 画像 3 枚が保存済みのキャラクター
- WHEN 生成をやり直す
- THEN 画像を新しく作り直す。新しい生成で作れなかった画像は、前の画像を残さず欠けたままにする
  (古い wav を削除するのと同じ扱い。前のプロフィールの絵が混ざらない)

### S0036_14 ほかのキャラクターの画像は変化しない [否定]

- GIVEN キャラクター C と D に画像が保存されている
- WHEN C の生成を行う
- THEN D の画像は**変化しない**(S0032_18 と同じ)

### S0036_15 縮小して PNG で保存する [境界]

- GIVEN 画像プロバイダーが 512x768 または 1024x1024 の画像を返した
- WHEN 保存する
- THEN 縦横比を保って 256x384 に収まる大きさ(512x768 → 256x384、1024x1024 → 256x256)に縮小し、PNG で保存する。
  256x384 に収まる画像は拡大しない。
  `local-sdcpp` の画像は、縮小のあとに背景を透明にして 7 色以下に減らす(`docs/integrations.md` S0046_09〜15)


## 要件: 生成を始めたときに、再開するか作り直すかを決める(論点 0038)

生成を始めたときに、保存されているプールから**再開**(S0020_06 / S0036_12)か**作り直し**(上の確定事項の表 / S0036_13)かを決める。
利用者が選ぶのではなく、状態から一意に決まる。判定に使うのはテキストの `completion` と「生成後にプロフィールを変えた」(S0032_22)だけで、
wav・画像の欠けは使わない。作り直す前の確認は `docs/main-window.md` S0038_07〜09。

### S0038_01 未完了のバケットが残っていれば再開する

- GIVEN キャラクター C の `pool.json` の `completion` に `pending` または `failed` が残っている。生成後にプロフィールを変えていない
- WHEN C の生成を開始する
- THEN 再開する。`complete` のバケットと保存済みの画像は作り直さず、未完了分から続ける(S0020_06 / S0036_12)

### S0038_02 全バケットが揃っていれば最初から作り直す

- GIVEN C の `completion` がすべて `complete`
- WHEN C の生成を開始する(作り直しの確認で作り直すを選んだ。`docs/main-window.md` S0038_07)
- THEN 全バケットを最初から作り直す。古い wav と画像は残さない(S0036_13)

### S0038_03 生成後にプロフィールを変えていれば、未完了でも作り直す [境界]

- GIVEN C の `completion` に `pending` が残り、生成後に C の名前・性格・話者のいずれかを変えた(S0032_22 の判定が立つ)
- WHEN C の生成を開始する
- THEN 再開せず、最初から作り直す。古いプロフィールで作った `complete` のバケットを**残さない**

### S0038_04 生成時のプロフィールを持たない未完了のプールは再開する [境界]

- GIVEN C の `completion` に `pending` が残り、プールが `generatedProfile` を持たない
- WHEN C の生成を開始する
- THEN 再開する(比べる元が無いので「変えた」と判定しない。S0032_23)

### S0038_05 プールが無い・読めないなら最初から作る [異常系]

- GIVEN C の `pool.json` が無い、壊れている、または `completion` を読めない
- WHEN C の生成を開始する
- THEN クラッシュせず、最初から作る

### S0038_06 画像だけが欠けていても、テキストが揃っていれば作り直す [境界]

- GIVEN C の `completion` がすべて `complete` で、画像が 1 枚以上欠けている(S0036_09 / S0036_10 で終わった)
- WHEN C の生成を開始する
- THEN 欠けた画像だけを作るのではなく、S0038_02 と同じく最初から作り直す(wav・画像の欠けは判定に使わない)

## 不変条件

- 生成の通信は **localhost のみ**(Ollama / VOICEVOX)。外部送信は発生しない。
- **応援発動経路は生成に依存しない**。読むのはプール + wav だけ。
  発動経路の配線(`src/main/index.ts`)から providers を import しない
  (キャラ作成は `characterCreationIpc.ts` に分離。ESLint で機械的に強制)。
- wav パスの解決は `resolveWavPath` に一本化する(生成側と発動側で規約を二重に持たない)。画像のパスの解決も同じく 1 箇所にまとめる。
- fs I/O はすべて main 側。core は純粋関数のまま。
- 生成の失敗は握り潰さない。完了していないプールを「完了」として扱わない。
