# ADR 0009: 応援トリガーの設定可能化と既定の緩和(2026-06)

## 文脈

応援の頻度は体験の核だが、当初設計では通常応援間隔(100 キーごと)もアクティブ判定(60 秒)もコードに固定されていた。
β 実利用想定では「100 キーは間隔が広すぎる」「離席判定 60 秒は短く誤判定が起きる」という体験課題が見え、固定値では吸収しきれない。
一方、KPM(直近 1 分の押下数)は「**分**」という単位の意味を保ちたい指標であり、設定値で動かすと表記が崩れる。

## 決定

- **`triggers.regular` の既定値を 100 → 50** に緩和。設定可能化(値域 1〜10000)。
- **`triggers.activeThresholdSec`(既定 60)** を設定値として新設。値域 5〜600(10 分)。
- **KPM 算出窓 = 60 秒固定**。`activeThresholdSec` とは**独立**(KPM は「分」の意味を保つ)。
- **マイルストーンも設定可能化**(各値 1 以上・昇順・重複なし・最大 20 個、空配列 = milestone OFF を許容)。
- **マイグレーション**: 既存ユーザーの `triggers.regular = 100` はアップデート時に **50 にリセット**し、起動時に通知する(新既定の体験を一律で届けるため。以降ユーザーが明示変更した値は尊重)。
- **不正値防御**: engine 側純粋関数 `validateTriggerConfig()` を起動時に走らせる。設定 JSON を直接編集された場合も既定値に置換しログを残す。
- **即時反映**: engine は設定値を引数で受け取る純粋関数。設定保存後は次のキー押下から新値で判定。再起動不要。

## 結果

- 利点:
  - ユーザーごとの「ちょうど良さ」を吸収できる(個人差の大きい指標を固定値で縛る無理がなくなる)。
  - 既定を 50 に緩めることで β 期の初印象が向上(発動間隔が短く、すぐ応援を体感できる)。
  - KPM の「分」表記が壊れない(`activeThresholdSec` だけ伸ばせる)。
  - マイルストーン空配列許容により「派手な節目演出は不要」というユーザーニーズに対応。
- 欠点 / トレードオフ:
  - マイグレーション(100 → 50 リセット)は既存ユーザーには変化として現れる。通知でカバーするが、サプライズはある。
  - 設定 UI が 1 タブ増える(トリガー設定タブ)。
  - 値域バリデーション・即時反映のための main/engine 連携(設定変更通知)が必要。

## 比較した選択肢

- **KPM 窓も `activeThresholdSec` に連動させる**: 設定が 1 つで済むが、「分」という単位の意味が崩れて UI 表記が嘘になる。却下。
- **既存 100 をそのまま保持(マイグレーションしない)**: 安全だが、新既定値が活きるのは新規ユーザーだけになる。β 体験改善の意図と合わない。却下。
- **マイルストーン空配列禁止**: 常に何かの節目応援を出す前提になり、UI 側でも 1 件削除時のガードが要る。許容の方がシンプル。

## 関連 ADR への影響

- **ADR 0006(速度ゾーン応援)**: 速度ゾーン閾値(slow/normal/fast = 100/250)は影響なし(本変更の対象外。設定可能化の有無は別 change で判断する)。
  ただし 0006 が決めた「**アクティブ時間判定 = 60 秒固定**」は本 ADR で **`triggers.activeThresholdSec`(既定 60、設定可能)に置き換わる**。KPM の 60 秒窓は 0006 のまま固定。
- **ADR 0007(オフライン応援プール)**: 影響なし。プール構造とシナリオキーは不変。`triggers.regular` 既定変更により「50 キーごとに 1 文消費」する頻度に上がるが、24 バケット × 8 文(=192 文。2026-07-26 に 20 文から引き下げ → ADR 0007 の追記)+ 連続回避(セッション内除外)で対応可能。
- **ADR 0008(外部 API プロバイダー)**: 影響なし。

## 未確定事項 [要確認]

- 値域上限の妥当性(通常 10000 / アクティブ 600 / マイルストーン 20)は β 実測で再評価。
- マイグレーション通知の文言(「既定値が 50 に変わりました。設定>トリガーから変更できます」程度を想定)。
