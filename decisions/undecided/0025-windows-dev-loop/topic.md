# 論点 0025: 開発から Windows 実機確認までのループをどう一本化するか

- **種別: 決定的**
- **状態: 未決定**
- **反映先: —**(開発手順であって製品の要件に及ばない。決めた内容は `DEVELOPMENT.md`・
  `.claude/rules/stack.md`「Commands」・`package.json` の scripts へ)

## 何を決めるか

**構成と起動の管理を一箇所にまとめ、開発と Windows 実機確認のあいだの「ビルドと移動」を
短くする方法。** Docker は手段の 1 つであって目的ではない(全部を Docker にする必要はない)。

いま実機確認が止まっている作業が実際にある — `work/0004-pool-generation-and-playback` の
残タスクは「Windows 実機で『フォーム入力 → ローカル生成 → 打鍵で生成した文言と声で応援』を
確認する」だけで、他は緑。**確認の手順が無いことがボトルネックになっている。**

## 現状の実測(2026-08-16 時点)

| 事実 | 状態 | 出典 |
| --- | --- | --- |
| Windows から WSL2 の :11434 / :50021 | **到達できる**(どちらも HTTP 200) | 実測 |
| `uiohook-napi` の Windows prebuild | **同梱されている**(`prebuilds/win32-x64`) | `node_modules` |
| `package.json` の `build`(electron-builder 設定) | **無い** | `package.json` |
| wine(Linux から Windows インストーラを作るのに要る) | **無い** | 実測 |
| electron / electron-builder | 43.2.0 / 26.15.3 | `package.json` |
| `/mnt/c`(WSL2 から Windows のファイルへ) | アクセスできる | 実測 |

ここから言えること。

- **ランタイム側の「移動」問題は論点 0023 で既に解けている。** Windows で動かすアプリからでも、
  WSL2 の Docker コンテナへ `127.0.0.1` でそのまま繋がる。**compose を触る必要は無い。**
- **ネイティブモジュールはクロスパッケージできる。** `uiohook-napi` が win32-x64 の prebuild を
  持つので、Linux 側でパッケージしても Windows 用のバイナリが入る(再ビルド不要)。
- **wine が無いので NSIS インストーラは Linux から作れない。** ただし `--win --dir`
  (展開済みフォルダ)なら作れる。**実機確認には installer は要らない** — フォルダを
  `/mnt/c` へ置いて `.exe` を叩けばよい。
- **本当に足りないのは electron-builder の設定そのもの。** 現状 Windows 向けに固める手順が
  ゼロから存在しない。どの案を採っても、この設定を書くことは共通で必要になる。

## 範囲(混同しないもの)

- **配布インストーラは本論点の対象外。** 論点 0010(ランタイム同梱・重みは初回取得)で決めた
  配布形態の実装は未着手のままで、ここで決めるのは**開発中の実機確認用の成果物**まで。
  インストーラを作る段になったら 0010 の反映作業として別に切る。
- **Electron 自体をコンテナで「実行」する案は採らない**(下の「却下する方向」)。

## 却下する方向(先に潰しておく)

**アプリをコンテナ内で実行する構成は、既存の不変条件に正面から反する。**

- **グローバルキーフックが機能しない。** Linux コンテナから Windows ホストの打鍵は捕捉できない。
  キーの種類を数えることがこのアプリの中核機能なので、確認したいものがまさに確認できなくなる。
- **`safeStorage` が平文相当に落ちる。** コンテナ内には Windows Credential Manager も keyring も
  無く、Electron の safeStorage は `basic_text` にフォールバックする。
  「API キーは `safeStorage`。平文 JSON に出さない」は
  @.claude/rules/security-rules.md「このプロジェクト固有」の**絶対の制約**として書かれている。

ビルドとテストだけをコンテナに入れるなら、このどちらにも触れない。

## 案

| | 案A: npm scripts に一本化(Docker 追加なし) | 案B: ビルド専用コンテナを足す | 案C: Windows 側でビルドする |
| --- | --- | --- | --- |
| 追加する依存 | 無し | Node/electron-builder を載せたイメージ | Windows に Node を導入 |
| Node 版の固定 | ホストの Node 任せ | **コンテナで固定できる** | Windows 側でもう一度固定が要る |
| インストーラ(NSIS) | 作れない(wine 無し) | イメージに wine を入れれば作れる | **作れる**(0010 の実装で効く) |
| 実機確認用の `--dir` | 作れる | 作れる | 作れる |
| 手順の数 | 1 コマンド | 1 コマンド | 環境が 2 つに増える |
| 構成の正本 | `package.json` + `compose.yaml` | 同左 + Dockerfile | 同左 + Windows 側手順 |
| 0010(配布)への効き | 弱い(後で別途 wine か Windows が要る) | 中 | **強い** |

どの案でも共通して必要なもの:

1. `package.json` に electron-builder の `build` 設定(`win` ターゲット、`files`、出力先)。
2. 成果物を `/mnt/c` 配下へ置くコマンド(移動を手作業にしない)。
3. `stack.md`「Commands」への追記(コマンドの正本を 2 系統にしない)。

## 決めるべき細目

1. **成果物の置き場。** `/mnt/c` のどこに置くか。**手元固有の絶対パスを追跡ファイルに書かない**
   (論点 0023 の細目 4 と同じ理由)ので、環境変数か既定値 + 上書きの形にする必要がある。
2. **`asar` と `files` の範囲。** `dist/` だけで足りるか、`node_modules` の prebuild を
   どう含めるか。
3. **実機確認時のランタイム接続先。** 既定の `system.ollamaEndpoint` / `voicevoxEndpoint` が
   `127.0.0.1` のままで Windows から通ることは実測済み。**設定変更は不要**という確認で足りるか、
   シナリオとして固定するか。

## 現在の考え

**案A が最小で、いま止まっている work/0004 の実機確認を最短で解ける。** ランタイムは既に
繋がっていて、ネイティブモジュールもクロスパッケージできるので、足りないのは
electron-builder の設定と配置コマンドだけ。

案B は Node 版まで固定できる点が魅力だが、**いま困っているのは再現性ではなく手順の不在**なので、
先に案A で通してから必要になった時点で足すほうが順序として素直。
案C は 0010(配布インストーラ)には効くが、実機確認のためだけに環境をもう 1 つ増やすのは重い。

**待っているもの**:人間の選択。とくに「インストーラ作成(0010 の実装)をどれくらい先に見据えるか」で
案B・案C の価値が変わるので、そこは方針として決めてもらう必要がある。
