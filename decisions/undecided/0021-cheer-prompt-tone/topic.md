# 論点 0021: 応援プロンプトに速度ゾーンを含めるか

- **種別: 非決定的**
- **状態: 未決定**
- **反映先: —**(決めた値は config へ。要件には及ばない)

## 何を決めるか

キャラ作成時の一括生成で、プロンプトに速度ゾーン(slow / normal / fast)と当日アクティブ時間を
明示的に含めるかどうか。含めた方が状況に合った文言になるはずだが、**良し悪しは指標でしか測れない**
ため、決定的な要件としては書かない(@.claude/rules/experiment-rules.md)。

## 案

| | 案A: zone_aware(ゾーンを渡す) | 案B: zone_blind(渡さない = 現行) |
|---|---|---|
| 状況適合度 | 上がるはず(仮説) | 現行水準 |
| 生成レイテンシ | プロンプトが伸びる分わずかに増える | 現行水準 |
| プール構造への影響 | 無し(バケットは元からゾーン別) | 無し |

## 測り方

- 評価データ: 代表的な状況サンプル 30 件(count / type / timeOfDay / kpm / zone の組み合わせ)
- モデル: sarashina2.2-3b-instruct(固定。論点 0027 で gemma2:2b から変更、Gemma は使わない方針)、temperature 0.8 固定、seed 42 固定、依存は `package-lock.json` で固定
- 試行: 各サンプル 5 生成 = 150 メッセージ
- 指標: 状況適合度(人手 1〜5 スコアの平均)/ 多様性(同一サンプル内のユニーク率)/
  1メッセージあたり生成レイテンシ(ms)/ 契約違反率(30文字超過・空・複数文)
- 比較基準(baseline): `src/core/baseline/messages.ts` の同梱定型文と、ゾーンを渡さない現行プロンプト。
  baseline は固定し、改良したいときは別名で追加する(@.claude/rules/experiment-rules.md「規律」)。
- 計測コマンド: `npm run eval`

## 中止条件

- 一括生成の総時間がキャラ作成の待ち時間として許容できない水準を超えたら中止し、現行プロンプトに戻す。
- 契約違反率が baseline より悪化したら中止(品質以前の問題)。

## 却下した案

- 発動のたびに生成してレイテンシを測る案 — 論点 0007 で発動時生成そのものを廃止したため無効。
  レイテンシはキャラ作成時の一括生成コストとしてのみ意味を持つ。
- 当日アクティブ時間をプロンプトに渡す案 — プールは事前生成なので、生成時点の値は発動時の状況と一致しない
  (人間の判断 2026-10-31。測らずに捨てた)。

## 現在の考え

**前提が現行のコードと食い違っている(2026-10-25 に確認)。** 案B を「zone_blind = 現行」としているが、
現行の `buildSystemPrompt` は**すでにゾーンを渡している** — バケットキー `{normal_regular_morning}`
(ゾーンと時間帯を含む)と `速度ゾーンでテンション調整: slow=… / normal=… / fast=…` の行がある。
また評価データ「状況サンプル 30 件(count / kpm …)」は、発動時生成をやめて
バケット単位の一括生成になった(論点 0007)後の形と合っていない。

**人間の判断(2026-10-31):これ以上は足さない(現行維持)。測らずに止める。**
ゾーンは現行のプロンプトにすでに入っている。当日アクティブ時間はプールを事前生成するため、
生成時点の値を渡しても意味が無い。どちらの向きでも、この論点が測ろうとしたものは残っていない。
プロンプトは論点 0026 の決定(書式の指示を足さない)のとおり現行のままにする。

**`undecided/` に置いたままにしている理由**:非決定的な論点は実測値が無いと `decided/` に移せない
(`/decide` の停止条件)。`result.md` は未計測のままで、数値を埋めて決めたように見せない。
**再開の条件**:ゾーンの行を消す案(現行を baseline、zone_blind を variant)を測りたくなったら、
ここで測り方を書き直して再開する。計測ドライバ(`src/eval/`、`axis: prompt`)はそのまま使える。
