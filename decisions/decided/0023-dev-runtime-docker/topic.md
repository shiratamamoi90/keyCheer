# 論点 0023: 開発環境の Ollama / VOICEVOX を Docker で管理するか

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: —**(開発環境の構成であって製品の要件に及ばない。決めた内容は `DEVELOPMENT.md`
  「開発環境のセットアップ」と `.claude/rules/stack.md`「動作前提」へ反映する)

## 何を決めるか

開発中に Ollama(:11434)と VOICEVOX(:50021)をどう起動し、**どのバージョンに固定するか**。

現状 `.claude/rules/stack.md`「動作前提」は「**現状の開発では Ollama / VOICEVOX を手元で別途起動する**」
とだけ書いており、バージョンが人・時期によって変わる。これは不変条件「再現性」
(@.claude/rules/impl-rules.md「不変条件」— 依存バージョンを固定する)を満たしていない。

決めないと先に進めない理由は 2 つ。

1. **論点 0022 の反映作業に要る。** `generatedBy` は「その種別が**欠損なく完了**したか」で記録を
   分けるため(S0022_02 / S0022_03)、プール生成と wav 合成が実際に走る環境が要る。
   両サービスが無いと、部分成功と完全成功の切り分けを実機で確認できない。
2. **論点 0021 の計測に要る。** 生成レイテンシを測る以上、測定対象のバージョンが動くたびに
   変わっていては `result.md` に数値を残せない(@.claude/rules/experiment-rules.md)。

**Docker 自体が新規依存**になるため、採用の審査結果もここに残す
(@.claude/rules/security-rules.md「依存・サプライチェーン」)。

## 新規依存の審査

| | Ollama | VOICEVOX ENGINE | Docker / Compose |
|---|---|---|---|
| 出所 | `ollama/ollama`(公式) | `voicevox/voicevox_engine`(公式) | 開発機に導入済み(29.7.1 / Compose v5.4.0) |
| 最新の安定版 | **0.32.13**(2026-08-14) | **0.25.2** | — |
| 採らないもの | `0.32.14-rc0`(RC) | `0.26.0-dev`(dev)・`latest` | — |
| 位置づけ | **開発環境のみ**。製品には同梱しない | 同左 | 同左 |

- Ollama / VOICEVOX は**既に採用済みの依存**(論点 0002 / 0003)。本論点で新しく入るのは
  **Docker による起動・固定の仕組み**だけで、製品が話す相手は変わらない。
- **配布形態(論点 0010)は変えない。** 0010 は「ランタイム実行ファイルは同梱、モデル重みは
  初回セットアップ時に取得」で確定しており、**利用者に Docker を要求しない**。
  ここで決めるのは開発機の話に限る。**この 2 つを混同しない。**
- ポートは `docs/integrations.md` の契約どおり :11434 / :50021 を維持する
  (変えると契約側の変更になり、本論点の範囲を超える)。

## 開発機の実測(2026-08-16 時点)

| 項目 | 値 |
|---|---|
| GPU | NVIDIA GeForce RTX 4070 Laptop 8188 MiB |
| Docker の GPU 対応 | nvidia runtime + CDI(`nvidia.com/gpu=all`)有効 |
| CPU / メモリ | 16 コア / 15 GiB |
| 現在の :11434 / :50021 | どちらも応答なし(未起動) |

**製品ターゲットは iGPU/CPU**(@.claude/rules/stack.md「Stack」の環境)。開発機の GPU は
ターゲットより強いため、**どちらのイメージで回すかが計測の代表性に直結する。**

## 案

| | 案A: Compose で CPU 既定 + GPU プロファイル | 案B: Compose で GPU 既定 | 案C: 手元インストールのまま手順書で固定 |
|---|---|---|---|
| 再現性 | イメージタグ + digest で固定 | 同左 | 手順書頼み。実際の版はマシン任せ |
| 既定の実行環境 | CPU(ターゲットに近い) | GPU(開発機に最適) | マシンごとにばらばら |
| 計測の代表性(論点 0021) | 既定のまま測れる | **GPU の数値になり代表性を失う** | 版が揺れるので測れない |
| 生成の待ち時間(開発中) | 遅い(gemma2:2b の CPU 推論) | 速い | マシン次第 |
| 新規依存 | Docker | Docker | 無し |
| 切り替え | `--profile gpu` で明示的に切替 | CPU に戻す手段が要る | — |
| 配布(論点 0010)への影響 | 無し | 無し | 無し |
| 初回のディスク | CPU イメージ + 重み | GPU イメージ(より大)+ 重み | 重みのみ |

## 論点に含まれる細目(案が決まったら一緒に確定する)

1. **バージョン固定の粒度。** タグのみか、**タグ + digest** か。security-rules「依存・
   サプライチェーン」と不変条件「再現性」からは digest まで固定するのが素直だが、更新のたびに
   digest を取り直す手間が増える。
2. **モデル重み(`gemma2:2b`)の置き場と固定。** 名前付きボリュームに置いて再取得を避けるか、
   ホストにバインドするか。重みは `.gitignore` 区分2で既に除外対象(`models/` `*.gguf`)。
3. **compose ファイルを git 追跡するか。** 自分で書いた成果物なので既定では追跡される
   (`.gitignore` の追跡方針)。追跡するなら**手元固有の値を書かない**。
4. **起動を `npm run` から叩けるようにするか**(`stack.md`「Commands」に行が増える)。

## 現在の考え

案C は Docker を増やさない点だけが利点で、**再現性の不変条件を満たせない**ため本命ではない。
案A と案B の差は実質「既定をどちらにするか」で、どちらでも profile を書けば両方使える。

**待っているもの**:人間の選択。とくに「開発中の待ち時間」と「計測の代表性」のどちらを既定に
置くかは好みではなく方針の問題なので、勝手に決めない。

なお **論点 0021 の計測を何の上で行うか**は本論点では決めない。計測条件は 0021 の
「測り方」が持つべきもので(モデル・seed・依存を固定する条項が既にある)、本論点が決めるのは
**開発環境の既定**まで。0021 側に「計測は CPU 構成で行う」等の条項が要るなら、そちらへ追記する。

## 決定

**案A を採る。開発環境の Ollama / VOICEVOX を Docker Compose で固定管理し、既定は CPU とする。**

1. **既定は CPU で、ずっと CPU で回す。** 製品ターゲット(iGPU/CPU)に合わせる。
   GPU は `--profile gpu` で明示的に叩いたときだけ使える逃げ道として残し、**既定には戻さない**。
2. **バージョンはタグ + digest で固定する。**
   - `ollama/ollama:0.32.13@sha256:77f1a2a54460f0380f2611e1464233d9b82cb6e58afc8f60abec0061049d2d82`
   - `voicevox/voicevox_engine:cpu-0.25.2@sha256:eb8c7f46a7d01217d1ff2b6f018261faedeceded3cc756b4fbbf371791ad6c90`
3. **モデル重み(`gemma2:2b`)は名前付きボリュームに置く。** コンテナを作り直しても再取得しない。
4. **compose ファイルは git 追跡する。** 手元固有の値(絶対パス・ポート変更・鍵)を書かない。
5. **起動は `npm run` から叩けるようにする。** コマンドの正本は
   `.claude/rules/stack.md`「Commands」なので、そちらにも行を足す。
6. ポートは `docs/integrations.md` の契約どおり :11434 / :50021 を維持する。

> 細目 2〜5 は論点本文の「論点に含まれる細目」で挙げたもの。**いずれも既存ルールから一意に
> 導けるため、この決定に含めた**(下の「理由」参照)。判断が違うなら新しい論点で覆す。

## 理由

- **既定を CPU にするのは、開発機(RTX 4070 Laptop)がターゲットより強いから。** GPU を既定にすると
  「開発機では速い」状態が普通になり、iGPU/CPU 機での待ち時間に気づけない。論点 0021 の
  レイテンシ計測も、既定の構成のまま測れるほうが条件を揃えやすい。開発中の待ち時間は
  そのコストとして受け入れる。
- **案A と案B の差は既定だけ**で、どちらも profile を書けば両方使える。ならば
  「気づきにくい側」を既定から外すほうが安全。
- **digest まで固定するのは、タグが動くから。** タグは同じ名前のまま中身が差し替わりうるので、
  タグだけでは不変条件「再現性」(@.claude/rules/impl-rules.md)を満たさない。
  security-rules.md「依存・サプライチェーン」のバージョン固定もここに掛かる。
  更新時に digest を取り直す手間は、再現できない環境で計測する損失より小さい。
- **重みを名前付きボリュームに置くのは、`.gitignore` 区分2が既に `models/` `*.gguf` を
  除外しているから。** リポジトリに落とす前提を作らない。ホストへのバインドにすると
  手元固有の絶対パスが compose に混ざる(細目 4 と衝突する)。
- **compose を追跡するのは、`.gitignore` の追跡方針で「自分が書いた成果物」に当たるから。**
  除外対象(区分3)はフォーマット同梱物であって、このファイルはそれではない。
- **`npm run` から叩けるようにするのは、コマンドの入口を 1 箇所に揃えるため。**
  `stack.md`「Commands」が hooks / skill の呼ぶコマンドの正本になっているので、
  起動手順だけ別系統(素の `docker compose` を手で打つ)にすると正本が 2 つになる。

## 却下した案

- **案B(GPU 既定)** — 開発は速いが、開発機だけターゲットより強い条件が常態になる。
  iGPU/CPU 機での待ち時間に気づけず、論点 0021 の計測も別条件を用意する必要が出る。
  GPU 自体は profile として残すので、必要なときは使える。
- **案C(手元インストールのまま手順書で固定)** — Docker を増やさない点だけが利点。
  実際の版がマシン任せになり、**不変条件「再現性」を満たせない**。手順書は強制力が無く、
  「書いてあるが揃っていない」状態を検出できない。
- **タグのみの固定** — 手間は減るが、タグは中身が差し替わりうるため固定にならない。
- **重みをホストにバインド** — 手元固有の絶対パスが compose に入り、git 追跡と両立しない。

## 決まらなかったこと(次の論点へ)

- **論点 0021 の計測条件**(何の上で測るか)は本論点では決めない。本論点が決めたのは
  開発環境の既定までで、計測条件は 0021 の「測り方」が持つ。既定が CPU に決まったので、
  0021 側は既定のまま測れる — 追記が要るかは 0021 を再開するときに判断する。
- **配布物への Docker 利用は検討していない。** 論点 0010(ランタイム同梱・重みは初回取得)は
  変えておらず、利用者に Docker を要求しない。変えるなら別の論点を開く。
