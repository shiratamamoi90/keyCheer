# 論点 0021: 応援プロンプトに速度ゾーンを含めるか

- **種別: 非決定的**
- **状態: 決定済み**
- **反映先: —**(決めた値は config へ。要件には及ばない)

## 何を決めるか

キャラ作成時の一括生成で、プロンプトに速度ゾーン(slow / normal / fast)と当日アクティブ時間を
明示的に含めるかどうか。含めた方が状況に合った文言になるはずだが、**良し悪しは指標でしか測れない**
ため、決定的な要件としては書かない(@.claude/rules/experiment-rules.md)。

## 案

**2026-10-31 に測り方を書き直した。** 当初の案B「zone_blind = 現行」は現行のコードと食い違っていた
(現行の `buildSystemPrompt` は既にゾーンを渡している。下の「現在の考え」)。現行を baseline にし、
ゾーンの行を消した案を variant にして測る。

| | baseline: zone_line(現行) | variant: no_zone_line |
|---|---|---|
| プロンプト | 「速度ゾーンでテンション調整: slow=寄り添う / normal=標準 / fast=勢いを煽る」の行がある | その 1 行だけを消す |
| バケットキー `{slow_regular_morning}` 等 | 渡す | 渡す(同じ) |
| 仮説 | ゾーンごとにテンションが分かれる | ゾーンの差が薄れる。プロンプトが短い分わずかに速い |

## 測り方

- 振る変数:上の 1 行の有無だけ(`axis: prompt`。案は `src/eval/promptVariant.ts`)。
- 評価データ:24 バケット × 評価用キャラクター 3 種(`src/eval/textModelComparison.ts` の `EVAL_CHARACTERS`)。
- モデル:sarashina2.2-3b-instruct(Ollama、q4_K_M)、temperature は Ollama 既定、seed 42(試行 i は seed + i)、
  構造化出力あり(論点 0024)。依存は `package-lock.json`、ランタイムは compose.yaml の ollama(digest 固定、CPU)。
- 試行:各バケット 5 回 = 各案 360 バケット。
- 指標(自動):30 字超過率・失敗バケット率・件数充足率・日本語の文の率・書式混入率・平均レイテンシ
  (論点 0026 と同じ集計)。
- 指標(人手):**ゾーンの適合**。同じキャラ・同じ種別・同じ時間帯で slow / normal / fast の文を両案で並べた見本を
  `result.md` に載せ、人間が「ゾーンごとにテンションが分かれているか」を判断する。
- 計測コマンド:`npm run eval -- decisions/undecided/0021-cheer-prompt-tone`

## 中止条件

- variant の契約違反(30 字超過率・失敗バケット率)が baseline より明らかに悪化したら、現行に戻す(= 現行維持)。

## 決定

ゾーンの行を残す(現行の `buildSystemPrompt` のまま。案 zone_line)。

## 理由

- 計測(`result.md`)で、ゾーンの行がテンションの差を作っていると分かった。「!」の数は slow → fast で
  0.40 → 0.77、勢いの語は fast だけ 14.2%。行を消すと差はほぼ消える(0.49 → 0.63、勢いの語 1.3% 以下)。
- 行を消すと 30 字超過も 2.8% → 5.1% に増える。
- ゾーン名の漏れ(9.7% のバケット)は行を残すことで続く欠陥だが、行を消して直すとゾーンの差も失う。
  漏れは「ゾーン名をどう書くか」で直せる見込みがあるので、論点 0035 で測る(人間の判断 2026-10-31)。

## 却下した案

- no_zone_line(ゾーンの行を消す)— ゾーン名の漏れは 0 になるが、ゾーンごとのテンションの差がほぼ消え、
  30 字超過も増えた(`result.md`)。漏れは書き方を変えて直す道が残っている。
- 発動のたびに生成してレイテンシを測る案 — 論点 0007 で発動時生成そのものを廃止したため無効。
  レイテンシはキャラ作成時の一括生成コストとしてのみ意味を持つ。
- 当日アクティブ時間をプロンプトに渡す案 — プールは事前生成なので、生成時点の値は発動時の状況と一致しない
  (人間の判断 2026-10-31。測らずに捨てた)。

## 決まらなかったこと(次の論点へ)

- ゾーン名 `slow` / `normal` / `fast` が応援文に漏れる欠陥の直し方 → 論点 0035(行を残し、ゾーン名を日本語で書く案を測る)。

## 現在の考え

**2026-10-31 に計測し(`result.md`)、人間の判断で決定した(上の「決定」)。**
ゾーンの行はテンションの差を作っている一方で、ゾーン名 `slow` / `normal` / `fast` が 9.7% のバケットで
応援文に漏れている(現行の欠陥)。行を消すと漏れは 0 になるが、ゾーンの差はほぼ消え、30 字超過がやや増える。
人間は「行を残してゾーン名を日本語にする案を別の論点で測る」を選んだ。

経緯:2026-10-25 に、元の案B「zone_blind = 現行」が現行のコードと食い違っている(現行は既にゾーンを渡している)と
分かり、2026-10-31 にいったん測らずに止めた。その後、測ってから決めることになり、現行を baseline、
ゾーンの行を消した案を variant にして測り方を書き直した。
