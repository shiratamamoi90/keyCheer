# 論点 0080: 応援履歴(`cheerHistory`)の記録をやめる

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: `docs/cheer-trigger.md`・`docs/data-model.md`・`docs/character-selection.md`・`docs/overview.md`**

## 何を決めるか

応援が出るたびに `stats.cheerHistory` へ 1 件足しているが(S0013_12)、消す仕組みが無く、読む画面も無い
(統計 UI は当面作らない。人間の判断 2026-11-27)。`docs/data-model.md`「検討事項」の「統計肥大化時の保持期間・集約方針(未検討)」が
これに当たる。

- 通常の応援の既定は 50 回ごと。1 日 2 万打鍵なら 1 日約 400 件、1 件 200〜250 バイトで、1 年で約 15 万件・約 30 MB になる。
- `electron-store` は書き込むたびに設定ファイル全体を書き直す。統計は 10 秒ごとと応援のたびに書くので、そのたびに全体を書くことになる。
  設定・キャラクター・統計が同じ 1 ファイルなので、書き込みの途中で落ちたときに壊れる範囲も広がる。

人間は 2026-11-27 に、下の案のうち **B(記録をやめる)** を選んだ。この論点では、B にしたときに一緒に決めることを並べる。

## 案

| | 案A 上限を設ける | **案B 記録をやめる** | 案C 別ファイルに分ける |
|---|---|---|---|
| 大きくなるか | 上限で止まる | 増えない | 増え続ける |
| 将来の統計 UI の材料 | 残る | 無い(作るときに記録を始める) | 残る |
| 書き込みの量 | 上限ぶん毎回書く | 応援のたびの書き込みが無くなる | 別ファイルを毎回書く |
| 作る量 | 切り詰めの処理と上限の値 | 削るだけ | ファイルを分ける処理と移行 |

### 案B にしたときに決めること

1. **保存済みの `cheerHistory` をどうするか。**
   - B1:起動時に消す(`stats` から `cheerHistory` を取り除く。設定ファイルが小さくなる)。
   - B2:そのまま残す(読みも書きもしない。ファイルは小さくならない)。
   - 現在の考え:**B1**。残しても使い道がなく、大きくなった分が書き込みのたびに書かれ続ける。
     前の版の `secrets.json` / `audit.log.json` を起動時に消した論点 0054(S0054_01〜04)と同じ扱い。
     消すのは `cheerHistory` だけで、`totalKeyCount` などほかの統計には触れない。
2. **データ契約から `cheerHistory` を外すか。** 外す(`docs/data-model.md`「統計データ」の例から消す)。
   書かないのに契約に残すと、あるものとして読まれる。
3. **影響するシナリオ。**
   - S0013_12(履歴の記録)は欠番にする。
   - 「応援が出ても `cheerHistory` に記録しない」を [否定] で足す。
   - S0015_03 の GIVEN「cheerHistory に記録する speedZone」と、S0015_04 の GIVEN「cheerHistory・プールバケットキーに使う timeOfDay」は、
     `cheerHistory` を外して書き直す。速度ゾーンと時間帯は、プールのバケットキーとポップアップへの通知で使い続ける。
     書き直しは新しい ID で置き換えるか、文言だけ直すかを /decide で決める(ID は不変なので、意味が変わるなら置き換える)。
   - S0032_16 の「統計(キー押下数・応援履歴)」の括弧の中から「応援履歴」を外す。
4. **発動で確定する情報はどうなるか。** `kpm` / `speedZone` / `timeOfDay` / `messageId` はポップアップ・wav の再生・
   連続回避(直前 1 件のセッション内除外)で使うので残す。やめるのは永続化だけ。

## 決定

人間の決定(2026-11-27):「記録しない、削除する。機能も必要ない」。

1. **応援履歴(`stats.cheerHistory`)を記録しない**(案B)。応援が出てもポップアップ・wav の再生・連続回避は今までどおりで、
   応援 1 回ごとの記録だけをやめる。
2. **保存済みの `cheerHistory` は起動時に消す**(B1)。消すのは `cheerHistory` だけで、ほかの統計・設定・キャラクターには触れない。
3. データ契約(`docs/data-model.md`「統計データ」)から `cheerHistory` を外す。
4. S0013_12(履歴の記録)は欠番にする。S0015_03 / S0015_04 は ID を保ち、GIVEN から `cheerHistory` を外す
   (テストが見ているのは速度ゾーン・時間帯の値の一覧で、意味は変わらない)。S0032_16 の括弧から「応援履歴」を外す。

反映先のシナリオ:`docs/cheer-trigger.md` S0080_01、`docs/data-model.md` S0080_02〜04。

## 理由

- 読む画面が無く(統計 UI は当面作らない)、人間も応援履歴の機能は要らないと判断した。使われないデータのために設定ファイルが
  大きくなり続け、`electron-store` が書き込みのたびに全体を書き直す費用と、途中で落ちたときに壊れる範囲だけが増える。
- 保存済みの分を残しても使い道が無く、大きくなった分が書き込みのたびに書かれ続ける。前の版の残したファイルを起動時に消した
  論点 0054 と同じ扱いにした。

## 却下した案

- 案A(件数・期間に上限を設ける)— 将来の統計 UI の材料は残るが、その機能自体が要らない。上限の値と切り詰めの処理を
  作って保つ費用に見合わない。
- 案C(別ファイルに分ける)— 壊れる範囲は狭まるが、大きくなり続けることは止まらない。
- B2(保存済みの `cheerHistory` を残す)— 読みも書きもしないデータが設定ファイルに残り、書き込みのたびに書かれ続ける。

## 決まらなかったこと(次の論点へ)

- 統計を renderer に渡す `getStats()`(IPC `keycheer:get-stats`。`docs/popup.md` S0017_07 の preload API の一覧にある)は残る。
  呼んでいる画面は無い。外すかは、統計 UI を作らないことが固まったら別の論点で決める(今は開かない)。
- `dailyCounts` / `dailyActiveSeconds` は 1 日 1 件ずつ増え続ける(1 年で数 KB)。問題になったら論点を開く。
> 論点 0081 で片付けた(`getStats()` を消し、日ごとの記録もやめた)。
