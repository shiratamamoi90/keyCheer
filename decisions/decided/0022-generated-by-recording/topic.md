# 論点 0022: 生成元プロバイダー(`character.generatedBy`)をいつ・何で記録するか

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: `docs/integrations.md`(S0022_01〜08。S0016_34 を置き換え)/ `docs/data-model.md`(スキーマ)**

## 何を決めるか

`docs/integrations.md` S0016_34「生成元プロバイダーの保存」は決定済み要件だが、**実装もテストも
無い**(`scripts/validate.sh` が唯一の NG として報告し続けている)。要件は

> プール・音声・画像の生成が完了 → `character.generatedBy: { text, voice, image }` に記録される

と書いてあるが、現状では次の 2 点が決まらないと書き込めない。

1. **`image` に何を入れるか。** `Character.generatedBy` は 3 フィールドとも必須
   (`src/core/shared/types.ts`)。一方でキャラ画像生成は未実装で、キャラ作成フロー
   (`characterCreationIpc.ts`)が呼ぶのはテキストとボイスだけ。画像を 1 枚も作っていないのに
   `providers.image` の選択値を書くと、「そのキャラを作ったプロバイダー」という
   フィールドの意味が「選択されていたプロバイダー」にすり替わる。
2. **いつ書くか。** 現在キャラを書く経路は `store.saveCharacter`(プロフィールのみ)だけで、
   生成完了時に character を更新する経路が無い。テキストだけ成功しボイスが 0 本という
   部分成功(`missing > 0`)もあり、どの時点を「生成が完了」と見なすかで記録内容が変わる。

## 案

| | 案A: 種別ごとに生成完了時点で記録 | 案B: 生成完了時に選択値を一括で記録 | 案C: `image` を省略可能にする |
|---|---|---|---|
| `image` の扱い | 画像生成を実装するまで書かない(型を分ける) | 未実装でも `providers.image` を書く | 型を `Partial` 相当にし、作った種別だけ埋める |
| フィールドの意味 | 「実際に作ったプロバイダー」を保つ | 「選択されていたプロバイダー」に変わる | 「実際に作ったプロバイダー」を保つ |
| 部分成功(wav 0 本) | voice を記録しない判断が要る | 一括なので影響なし | voice を記録しない判断が要る |
| データ契約への影響 | `docs/data-model.md` のスキーマ変更が要る | 変更なし | スキーマ変更が要る(既存 JSON の後方互換も) |
| 実装量 | 中(store に更新経路 + 種別ごとの判定) | 小(成功時に 1 回書く) | 中 |
| 画像実装後の手直し | 不要 | `image` の意味を直す再論点が要る | 不要 |

## 現在の考え

要件の文言(「そのキャラを作った」)を素直に読むと案A / 案C。案B は今すぐ NG を消せるが、
画像生成を実装した時点で「選択値だったのか生成元だったのか」が混ざった JSON が既に
配布済みユーザーの手元に残る。データ契約は外から見える約束なので、後で意味を変えるのが
いちばん高くつく(@.claude/rules/doc-rules.md「何を仕様化するか」)。

**待っているもの**:キャラ画像生成(論点 0005 の実装)を先に着手するかどうか。先にやるなら
本論点は自然に案A で閉じる。当面やらないなら案C を選び、`docs/data-model.md` のスキーマと
既存 JSON の補完規則まで含めて決める必要がある。

## 決定

**案A を採る。`generatedBy` は種別ごとに、その種別の生成が欠損なく完了した時点で記録する。**

1. **各フィールドは任意。** 記録済みの種別だけが存在し、未生成・未実装の種別は**未設定のまま**にする。
   画像生成が未実装のうちは `image` を持たない。
2. **完全成功の判定は種別ごとに独立**(全種別ではない)。その種別に欠損が 1 つでもあれば
   その種別を記録せず、他の種別の記録は妨げない。
3. **フィールドの意味は「実際にそのキャラを作ったプロバイダー」。** `providers` の選択値ではない。
4. 既存 JSON に `generatedBy` が無い / 一部欠けている場合、**選択値で補完しない**(未設定のまま)。

## 理由

- 要件の文言「**そのキャラを作った**プロバイダー」を素直に読むと、作っていないものを書けない。
  案B は今すぐ NG を消せるが、画像生成を実装した時点で「選択値だったのか生成元だったのか」が
  混ざった JSON が既に配布済みユーザーの手元に残る。**データ契約は外から見える約束**であり、
  後から意味を変えるのがいちばん高くつく(@.claude/rules/doc-rules.md「何を仕様化するか」)。
- 判定を**全種別**にすると、画像生成が未実装である以上その条件は永久に成立せず、
  `generatedBy` が一度も書かれない。S0016_34 の NG も画像生成の実装まで残り続け、
  本論点を開いた目的(書き込む値を決めて要件を閉じる)を果たせない。**種別ごとの判定なら
  今の実装範囲(テキスト + ボイス)で完結する。**
- 部分成功をその種別の完了と見なさないのは、`generatedBy` の用途が**再生成時の参照**だから。
  欠損したまま「このプロバイダーで作った」と記録すると、再生成時に同じ欠損を再現しようとする
  余地が残る。**揃っているものだけを事実として残す。**
- 案A と案C はどちらも型を任意フィールドにする点で同じで、違いは**書き込みの時点**。
  種別ごとの完了時点に分けると、画像生成を後から足すときに**書き込み経路を1つ増やすだけ**で済む。

## 却下した案

- **案B(生成完了時に選択値を一括で記録)** — 実装は最小だが、フィールドの意味が
  「選択されていたプロバイダー」にすり替わる。画像生成の実装時に意味を直す再論点が必要になり、
  そのときには意味の混ざった JSON が配布済みユーザーの手元にある。上の「理由」1点目。
- **案C(`image` を省略可能にし、保存時に作った種別だけ埋める)** — 型の扱いは採用案と同じだが、
  書き込みが保存の 1 点に集まるため、種別ごとの完了時点を持たない。画像生成を足すときに
  「いつ書くか」を決め直すことになる。案A が上位互換なので採らない。
- **完全成功の判定を全種別で行う案** — 画像生成が未実装のため条件が永久に成立しない。
  実質「画像生成(論点 0005)を先に実装する」という宣言になり、本論点では決めきれない。

## 決まらなかったこと(次の論点へ)

- なし。部分成功(wav が 0 本 / 一部欠損)の扱いは**本論点で決めた**(上の決定 2)。
- 画像生成そのものの実装は論点 0005(決定済み)の反映作業であって、本論点の対象外。
  実装したときに `generatedBy.image` の書き込み経路を1つ足す(要件は S0022_04 が既に縛っている)。
