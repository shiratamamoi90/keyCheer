# 論点 0030: 利用者の機械にテキストモデルをどう入れるか(初回セットアップの取得物と、モデル定義の正本)

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: —**(取得物と取得元の決定。取得の振る舞いの要件は論点 0042 が `docs/model-weights.md` に反映する)

## 何を決めるか

論点 0010 は「`gemma2:2b` を初回セットアップでアプリが取得する」と決めている。論点 0027 で
`sarashina2.2-3b-instruct` に変えたので、**利用者の機械に何を・どこから取得させるか**を決め直す。

0027 は開発機で公式の重みを Ollama に取り込んで量子化した。利用者の機械で同じことをさせると、
約 6.7 GB を取得したうえで量子化の計算が要る。

## 案

| | 案A: 量子化済み GGUF を自分たちでホストする | 案B: 利用者の機械で取り込む | 案C: コミュニティの GGUF を取得させる |
|---|---|---|---|
| 取得量 | 約 2.1 GB(Q4_K_M) | 約 6.7 GB(BF16) | 約 2.1 GB |
| 利用者の機械の負荷 | 小 | 量子化の計算(CPU で時間がかかる) | 小 |
| 出所 | 自分たちで変換した GGUF(sha256 で固定) | 公式の重み | 第三者(0027 で却下) |
| 必要なもの | ホスト先(MIT なので再配布できる) | 無し | 無し |
| ライセンス表記 | MIT の LICENSE を同梱 | 同左 | 同左 |

## 人間の方針(2026-10-25)

**Gemma は使わない。削除する方針。** 論点 0027 で Sarashina に替えたあと、gemma2:2b を残して
選べるようにはしない。

方針から決まること:初回セットアップで gemma2:2b は取得しない(0010 の取得物から外す)。
Gemma の利用規約の同梱義務(0010)も無くなる。

## 併せて決める:モデル定義の正本(開発機と利用者の機械で共有する)

人間の指摘(2026-10-25):**モデルのインストールは開発機だけでなく利用者の機械も考える。**

モデルを入れるのに要る値は、今は開発機の `scripts/import-sarashina.sh` にしか無く、モデル名だけが
アプリの既定値(`DEFAULT_SYSTEM_CONFIG.ollamaModel`)と 2 箇所に直書きされている。利用者の機械で
入れる仕組み(初回セットアップ)を作ると、同じ値が 3 箇所目に出る(@.claude/rules/impl-rules.md
「共通化」— 3 箇所目は設計が要求している合図)。

| 値 | 開発機(0029) | 利用者の機械(本論点) | アプリの生成(0028) |
|---|---|---|---|
| Ollama 上のモデル名 | 使う | 使う | 使う(既定値) |
| チャットテンプレート・stop | 使う | 使う(案A でも案B でも Modelfile が要る) | 使わない |
| 取得元とハッシュ | 公式の重み(safetensors) | 案A なら量子化済み GGUF / 案B なら公式の重み | 使わない |
| 量子化の形式 | 使う | 案B なら使う | 使わない |

| | 案M1: モデル定義をデータファイル 1 つにまとめる | 案M2: 各所に直書きのまま |
|---|---|---|
| 置き方 | 例:モデル名・テンプレート・stop・取得元・ハッシュを持つ JSON を 1 つ置き、開発用スクリプト・初回セットアップ・既定値がそこから読む | 今のまま。コメントで「一致させる」と書く |
| 片方だけ直す事故 | 起きない | 起きうる(モデル名がずれると生成が「モデルが無い」で失敗する) |
| 依存方向 | 既定値は core にある。core はファイル I/O をしないので、JSON を import(ビルド時に取り込む)できるかの確認が要る | 影響なし |
| シェルスクリプトから読む | `node -e` で読む(jq は依存に足さない) | — |

あわせて、利用者の機械でも開発機と同じ GGUF になることを確かめられる:0029 の取り込みは
2 回とも同じ層 `sha256:60e33bab…6b959` を出した(再現できる)。案A でホストする GGUF はこの
sha256 で固定でき、開発機で作ったものと同じであることを照合できる。

## 議論の時点で確認が要った点(下の決定で解いた)

- 案A のホスト先(GitHub Releases / 自前の Hugging Face repo 等)。配布の手段そのものが未実装
  (electron-builder・初回セットアップ画面とも未実装)なので、それらの論点と順序を合わせる。
- Sarashina の MIT の LICENSE をどこに同梱するか(0010 のクレジット・規約の同梱と同じ置き場にするか)。
- モデル定義の正本を案M1 にするか。するなら置き場(core に置けるか)。
- 利用者の機械の Ollama は同梱ランタイム(0010)。初回セットアップで `ollama create` を実行する
  (案A なら GGUF + Modelfile、案B なら safetensors + 量子化)のか、Ollama の HTTP API(`/api/create`)で
  行うのか。

## 現在の考え(決定前の記録)

未決定。初回セットアップ画面と配布インストーラが未実装なので、急がない。案A が利用者の負荷で優る。
モデル定義は案M1 が、開発機・利用者の機械・アプリで同じ値を使えるので優る。

この論点が扱うのはテキストモデルの取得物と取得元だけ。画像の重みは論点 0041(どのモデルか)、
必須 / 任意の 2 段で取得する仕組み(論点 0036 が「0030 / 0010 で扱う」とした部分)は論点 0042 で決める。

## 決定

人間が承認(2026-11-11)。

1. **案A。量子化済みの GGUF(Q4_K_M、約 2.1 GB)を自分たちでホストし、利用者の機械はそれを取得する。**
   利用者の機械では量子化しない。gemma2:2b は取得しない(論点 0010 の取得物を置き換える)。
2. **ホスト先は Hugging Face の自分たちのリポジトリ。** 取得は版(コミット)を固定し、sha256 を照合する。
   開発機の取り込み(論点 0029)が 2 回とも出した層と同じものであることを照合してから置く。
3. **案M1。モデル定義(Ollama 上のモデル名・チャットテンプレート・stop・取得元・ハッシュ)を 1 つのデータにまとめ、**
   開発用スクリプト・利用者の機械での取り込み・アプリの既定値がそこから読む。
4. **利用者の機械での取り込みは Ollama の HTTP API で行う**(同梱ランタイムの CLI を別に叩かない)。

## 理由

- 案A は利用者の機械の負荷が最も小さい(取得 約 2.1 GB、量子化の計算なし)。MIT なので再配布できる。
- GitHub Releases は 1 ファイルの上限に収まらない見込みで、Hugging Face が素直(人間の判断)。
- 案M1 は、同じ値が開発機・利用者の機械・アプリの 3 箇所に出るのを防ぐ(@.claude/rules/impl-rules.md「共通化」)。
  モデル名がずれると生成が「モデルが無い」で失敗する。
- HTTP API にするのは、アプリが既に Ollama と HTTP で話しており、子プロセスの起動を増やさないため
  (同梱ランタイムの起動は論点 0034 の 1 経路だけにする)。

## 却下した案

- 案B(利用者の機械で公式の重みを取り込んで量子化する)— 取得 約 6.7 GB と量子化の計算を全員に負わせる。
- 案C(コミュニティの GGUF を取得させる)— 第三者の配布物。論点 0027 で却下済み。
- 案M2(各所に直書きのまま)— 片方だけ直す事故が起きうる。
- Gemma を残して選べるようにする — 人間の方針(2026-10-25)で使わない。

## 決まらなかったこと(次の論点へ)

- 取得の振る舞い(いつ・進捗・中断・照合・失敗)→ 論点 0042。
- Sarashina の MIT の LICENSE の置き場と表記 → 論点 0043。
- リポジトリ名・コミット・sha256 の値は、ホストした時点で本論点に追記する。
- モデル定義のデータの置き場と形式は構造の決定なので文書に書かない(コードが正本)。core はファイル I/O をしないので、
  ビルド時に取り込める形にする。
