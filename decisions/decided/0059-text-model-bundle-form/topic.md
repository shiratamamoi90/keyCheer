# 論点 0059: 配布物に入れるテキストモデルの形と、生成の前に照合するもの

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: `docs/model-weights.md`**(S0055_08 の照合の対象を具体化する。決まったら `docs/integrations.md` の同梱ランタイムの起動にも及ぶ)

## 何を決めるか

論点 0055 でテキストモデルも配布物に入れると決め、`docs/model-weights.md` S0055_08 に「置き場にテキストモデルが無い、または sha256 が
一致しなければ生成を始めない」と書いた。ところが**照合するファイル(名前・置き場・sha256)が決まっていない**ので、S0055_08 のテストも実装も書けない。

開発機では `npm run services:model`(`scripts/import-sarashina.sh`。論点 0029)が公式の safetensors を取得し、
Ollama のコンテナの中で `q4_K_M` に量子化して取り込んでいる。**配布物に入れる形のファイルは、まだ 1 つも作っていない。**

決めること:

1. 配布物に入れるテキストモデルの形(量子化済みの GGUF か、公式の safetensors か)
2. 置き場とファイル名(`{userData}/weights/text/…` か、インストール先か)
3. 何を sha256 で照合するか(GGUF 1 ファイルか、Ollama に取り込んだ後のモデルか)
4. 照合をいつするか(生成を始めるたびか、起動時に 1 回か)。GGUF 2 GB を毎回ハッシュすると数秒〜十数秒かかる

## 案

### 1〜3. 形と照合の対象

| | 案A:量子化済み GGUF を入れ、GGUF を照合する | 案B:公式の safetensors を入れ、利用者の機械で量子化する | 案C:GGUF を入れ、Ollama の取り込み後のモデルの digest を照合する |
| --- | --- | --- | --- |
| 配布物の大きさ | 約 2.1 GB | 約 6 GB(3B の bf16) | 約 2.1 GB |
| 利用者の機械の作業 | Ollama に取り込むだけ(数十秒) | 量子化(数分。CPU) | 取り込むだけ |
| 照合のしやすさ | ファイル 1 つの sha256。置き場で完結 | 3 ファイル | Ollama の API(`/api/show`)を通すので、Ollama が起動していないと照合できない |
| 再現性 | 論点 0030 で、取り込みが同じ層 `sha256:60e33bab…` を出すことを確かめてある | 同じ | 同じ |
| 論点 0030 との関係 | 0030 の案A(ホストしない以外は同じ) | 0030 の案B | — |

### 4. 照合の時

| | 案X:生成を始めるたびに照合する | 案Y:同梱ランタイムの起動の時に 1 回(結果を覚える) | 案Z:大きさだけ毎回見て、sha256 はインストールの時だけ |
| --- | --- | --- | --- |
| 待ち時間 | 毎回 数秒〜十数秒 | 起動の時だけ | ほぼ無し |
| 壊れたファイルに気づくか | 気づく | 起動の後に壊れたら気づかない | 中身の破損には気づかない |

## 現在の考え

決定済み(下)。

## 決定

人間が承認した(2026-11-24):**案A + 案X**。

1. 配布物に入れるテキストモデルは、**量子化済みの GGUF 1 ファイル**(sarashina2.2-3b-instruct の q4_K_M)。
2. 置き場は `{userData}/weights/text/`、ファイル名は `sarashina2.2-3b-instruct-q4_K_M.gguf`(画像の重みと同じ `{userData}/weights/` の下に、種類ごとのフォルダを切る。
   ファイル名はエージェントが補った)。
3. 照合するのは**その GGUF ファイルの sha256**。Ollama に取り込んだ後のモデルは照合しない。sha256 の値は、ビルドの時に GGUF を作る手順
   (配布インストーラの作業。論点 0031 / 0034)で作った物から固定し、この論点フォルダの `config.yaml` に記す。
4. 照合は**生成を始めるたびに**行う。前の照合の結果を覚えて使わない。

## 理由

- 案A は照合が置き場のファイル 1 つで完結し、Ollama が起動していなくても判定できる(S0055_08 を同梱ランタイムの状態から切り離せる)。
  配布物も約 2.1 GB で済み、利用者の機械で量子化する時間も要らない。
- 照合の時は、人間が「壊れたファイルに必ず気づく」ことを待ち時間(毎回 数秒〜十数秒)より優先した。生成はキャラ作成の時だけの操作で、
  もともと数分かかるため、十数秒の上乗せは受け入れる。応援の発動には照合が入らない(S0055_10)。

## 却下した案

- 案B(safetensors を入れ利用者の機械で量子化)— 配布物が約 6 GB になり、利用者の CPU で数分の量子化が要る。照合も 3 ファイルになる。
- 案C(取り込み後の digest を照合)— Ollama が起動していないと照合できず、S0055_08 の判定が同梱ランタイムの状態に依存する。
- 案Y(起動の時に 1 回)— 起動の後にファイルが壊れたり差し替えられたりしても気づかない。
- 案Z(大きさだけ毎回)— 中身の破損に気づかない。

## 決まらなかったこと(次の論点へ)

- GGUF をビルドの時に作る手順(コンテナで量子化して取り出す。論点 0030 の取り込みと同じ層 `sha256:60e33bab…` になるか)と sha256 の値 —
  配布インストーラの作業(論点 0031 / 0034)の中で作り、`config.yaml` に記す。
- GGUF を Ollama に取り込む時(インストール中か、同梱ランタイムの初回起動か)は論点 0055 の宿題のまま(論点 0034 の作業で決める)。
