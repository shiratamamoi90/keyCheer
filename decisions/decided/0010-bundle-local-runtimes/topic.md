# 論点 0010: ローカルランタイムの配布形態

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: —(配布形態の決定。初回セットアップの要件化は未着手)**

## 何を決めるか

Ollama / VOICEVOX / sd.cpp は「キャラ作成時のみ使う」生成ランタイム(論点 0002 / 0003 / 0005、
論点 0007 で用途を作成時のみに限定)。だが**誰がこれらを用意するのかが決まっていなかった**。

- `decisions/0003-tts-voicevox.md:14`:「別途インストール **or** 同梱(~200MB)が必要」— or のまま未確定
- `decisions/0002-local-llm-ollama.md`:「モデル取得(~1.6GB)が初回必要」— 取得の主体に言及なし
- `decisions/0005-image-gen-sdcpp-lcm.md:13`:「**同梱**」と明記(3 つのうちここだけ確定していた)
- `.claude/rules/stack.md:40`:「未起動でもクラッシュせずフォールバック」= 動作前提のみ保証

結果として、開発機に 1 つも導入されていない状態でも誰も気づかない状況が続いていた
(2026-07-26 時点で `ollama` / `voicevox` ともに未インストール、ポート 11434 / 50021 に待受なし)。

配布インストーラ(electron-builder)も未実装で、この判断は配布形態そのものに直結する。

## 決定

**ランタイム実行ファイルはアプリに同梱し、モデル重みは初回セットアップ時にアプリが取得する。**
どちらもユーザーに別途インストールを求めない。手作業で用意させるものはゼロにする。

| 区分 | 対象 | 入手方法 |
| --- | --- | --- |
| ランタイム(同梱) | Ollama 実行ファイル / VOICEVOX **ENGINE**(製品版エディタではない。理由は下記) / sd.cpp | インストーラに含める |
| モデル重み(初回取得) | `gemma2:2b` / VOICEVOX 音声ライブラリ / SD1.5 系ベースモデル + LCM LoRA(論点 0005 の既定) | 初回セットアップでアプリがダウンロード |

取得はアプリ内のセットアップ画面で行い、進捗を出し、中断・再開できるようにする。
ユーザーにコマンドを打たせない・配布ページから手動で落とさせない。

同梱ランタイムはアプリのライフサイクルで起動・停止し、ユーザーが個別に立ち上げる必要をなくす。
「キャラ作成時のみ子プロセスとして起動し、終わったら落とす」を基本とする(常駐させない)。

## 理由

- 「誰がランタイムを用意するのか」という本 論点 の主問題は、**別途インストールを求めない**ことで解決する。
  ここは同梱でも初回取得でも変わらず、ユーザー体験上の差は「待ち時間がいつ発生するか」だけ。
- 一方で**サイズの大半はモデル重みが占める**(下表)。ランタイムだけなら配布物は 1GB 前後に収まり、
  一般的なデスクトップアプリの範囲に留まる。重みまで同梱した 5〜8GB とは配布の現実味が違う。
- 応援発動はプール + wav のみで完結する(論点 0007)ため、**モデルが必要なのは初回のキャラ作成だけ**。
  オンラインを要求する場面がアプリの生涯で 1 回に限定でき、それ以降は完全オフラインを維持できる。
- パス解決・子プロセス起動という壊れやすい部分はランタイム側にあり、それは同梱で固定される。
  取得対象を重みファイルだけに絞れば、初回取得の失敗モードが「ダウンロードの成否」に単純化する。

## 「完全オフライン」の意味(定義の変更)

本 論点 により、これまでの「デフォルトで完全オフライン」は次の意味に狭まる:

- **初回セットアップのみオンラインを要する**(モデル重みの取得)。
- **それ以降は完全オフライン。** キャラ作成もプール生成も応援発動も外部通信ゼロ。
- 応援発動経路が永久に外部送信しないというプライバシー方針は**一切変更しない**。
  取得するのは公開モデル重みのみで、ユーザーのデータは送信しない。

README・CLAUDE.md・`.claude/rules/stack.md` の「完全オフライン」表現はこの定義に合わせる。

## トレードオフ

配布物と初回取得物の内訳(概算):

| 対象 | 概算サイズ | 区分 |
| --- | --- | --- |
| Ollama 実行ファイル | 300MB 〜 1GB(GPU ランタイムを含めるかで変動) | 同梱 |
| VOICEVOX ENGINE 本体(音声ライブラリを除く) | 200 〜 500MB(CPU 版) | 同梱 |
| sd.cpp 実行ファイル | 数十 MB | 同梱 |
| **配布インストーラ 小計** | **概ね 0.5 〜 1.5GB** | |
| gemma2:2b(q4 量子化) | 約 1.6GB | 初回取得 |
| VOICEVOX 音声ライブラリ | 数百 MB 〜 1GB(採用キャラ数による) | 初回取得 |
| SD1.5 系ベースモデル + LCM LoRA | 2 〜 4GB(量子化で変動) | 初回取得 |
| **初回取得 小計** | **概ね 4 〜 6.5GB** | |

**代償は「初回起動時にオンラインが必須になる」こと。** ディスク消費の総量は同梱案と変わらない。
移動した先が、インストーラのサイズから初回セットアップの待ち時間になっただけである。

そのため次が新たに課題になる:

- **初回取得が失敗した場合の扱い。** ネットワーク断・ミラー停止・ディスク不足で
  キャラ作成に到達できない。再開可能なダウンロードと明確なエラー提示が要る。
- **取得元の可用性に依存する。** 配布ミラーが消えると新規インストールが機能しなくなる。
  取得元を自前でホストするか、上流に依存するかの判断が要る(下記 [要確認])。
- **取得物の完全性検証。** ダウンロードした重みが改竄・破損していないことを
  ハッシュで検証する必要がある(同梱ならインストーラ署名で担保されていた部分)。
- オフライン環境のユーザーは初回セットアップができない。
  重み一式を別途配る「オフラインインストーラ」を用意するかは別途判断(下記 [要確認])。

## ライセンス上の制約(調査結果)

同梱は「技術的にできるか」より「**法的に許されるか**」が先に来る。調査した事実:

> **本 論点 の決定による影響**:モデル重みを**再配布しない**ことになったため、
> 重み側の再配布義務(Gemma Terms・OpenRAIL-M・音声ライブラリの再配布可否)は
> **大きく軽くなる**。ユーザーが上流から直接取得する形になるためである。
> ただし**利用条件・クレジット表記・Prohibited Use の flow-down は消えない**
> (アプリが取得を仲介し、生成物をアプリ内で使うため)。
> 一方 **VOICEVOX ENGINE 本体は引き続き同梱**なので、下記の LGPL の論点はそのまま残る。

### VOICEVOX — ここが最も注意を要する

- **製品版 VOICEVOX(エディタ)の利用規約は「本ソフトウェアの全てまたは一部を無断で
  再配布すること」を禁止している。** 製品版をそのまま同梱することはできない。
- 一方 **VOICEVOX ENGINE は デュアルライセンス**:LGPL v3、または
  ソース開示を要しない別途ライセンス(取得は開発者へ連絡)。
  → **同梱するなら製品版ではなく ENGINE を対象にする。**
- ENGINE は HTTP サーバーとして別プロセスで動くため、KeyCheer 本体とは
  リンクせずプロセス分離になる。LGPL の copyleft が本体へ及びにくい構成ではあるが、
  **これは法的判断であり、開発者側の確認を取るべき事項**。
- **音声ライブラリ(キャラの声)は 1 体ずつ個別規約**。同梱可否・商用利用可否は
  キャラごとに異なる。採用するキャラを決めてから 1 件ずつ確認が要る。
- **VOICEVOX を利用した旨のクレジット表記が必須**(生成物の利用時)。

### Gemma(gemma2:2b)

- Gemma Terms of Use。再配布・商用利用は可能だが、
  **Terms of Use のコピーまたは参照を同梱する義務**と、
  **Prohibited Use Policy の flow-down**(下流の利用者にも適用される)がある。
- なお Gemma 4 系は Apache 2.0 で条件が緩い。モデル選定を見直す余地がある。

### sd.cpp / SD1.5 系ベースモデル

- ベースモデルは CreativeML OpenRAIL-M 系が多く、モデルごとに条件が異なる。
  論点 0005 の `[要確認]`「同梱ベースモデルの最終選定(ライセンス/品質)」が未解決のまま。

## 開発環境

**同梱物と同じレイアウトを開発機でも使う。** 別途インストールした Ollama / VOICEVOX に
依存すると、開発機で通る配置と配布物の配置がずれ、パス解決や起動処理の不具合を
リリースまで検出できない。

- 同梱物は `vendor/`(git 追跡外)に置き、取得はセットアップスクリプトで行う。
- 開発時も配布時も**アプリから見た相対パスを同じにする**。
- ランタイム(同梱)とモデル重み(初回取得)で**配置先を分ける**。配布時に前者はインストーラ、
  後者はユーザーのマシン上で生成される。開発機でもこの 2 つを別ディレクトリにして、
  「同梱したつもりの重みを実は開発機のローカルから読んでいた」という取り違えを起こさない。
- 既に別途インストール済みの環境では、`system` 設定のエンドポイント上書きで
  そちらへ向けられる(現行実装のまま。`ollamaEndpoint` / `voicevoxEndpoint`)。

## 確定済み(2026-08-09)

- **配布サイズ**:5〜8GB の一括同梱は**採らない**。ランタイム同梱 + モデル重みの初回取得とする。
  → 本 論点 の「決定」に反映済み。

## 決まらなかったこと(次の論点へ)

法務(先に解く。技術判断より上流):

- **VOICEVOX ENGINE をどちらのライセンスで同梱するか**(LGPL v3 / 別途ライセンス)。
  LGPL を選ぶ場合、差し替え可能性とソース入手手段の提供をどう満たすか。**開発者への連絡が要る。**
- **採用する音声ライブラリ(キャラ)の選定と、その個別規約の確認**。
  再配布はしなくなったが、**利用条件と商用利用可否はキャラごとに残る**。
- **クレジット表記をどこに出すか**(アプリ内 / 生成物 / 配布ページ)。

初回取得の設計(本 論点 の決定から新たに生じた項目):

- **モデル重みの取得元をどこにするか。** 上流(Ollama レジストリ / VOICEVOX 配布 / Hugging Face)に
  直接向けるか、自前ミラーを立てるか。上流依存は可用性リスク、自前は転送コストと再配布の可否が絡む。
- **取得物の完全性検証の方式**(ハッシュの同梱と照合)。
- **初回取得の失敗・中断時の UX**(再開可能なダウンロード、部分取得状態からの復帰)。
- **オフラインインストーラを用意するか**(ネット不通環境向けに重み同梱版を別途配るか)。
- **どのモデルを必須とし、どれを任意とするか。** 画像生成(SD1.5 + LCM LoRA)は 2〜4GB と最も重く、
  キャラ画像は手動アップロードでも成立する。ここだけ任意取得にする余地がある。

その他:

- **Ollama の同梱形態**(実行ファイルをそのまま置くか、取得した重みをどこに配置するか)。
- **更新時の差分配信**(アプリ更新のたびに数 GB の重みを取り直さない仕組み)。
- モデル選定の見直し余地:**Gemma 4 系は Apache 2.0** で条件が緩い(論点 0002 の再検討)。

## 影響

- `.claude/rules/stack.md`「動作前提」を、ランタイム同梱 + 初回取得を前提とした記述に更新する。
- `README.md` / `CLAUDE.md` の「完全オフライン」表現を、上記「『完全オフライン』の意味」に合わせる
  (初回セットアップのみオンライン、以降は完全オフライン)。
- `README.md` のセットアップ手順に vendor 取得の手順が加わる。
- **初回セットアップ画面(取得の進捗・中断・再開・失敗表示)が新規の実装項目として発生する。**
  これは決定的な振る舞いなので仕様ループで扱う(別 change を切る)。
- 配布インストーラ(electron-builder)の設計は、上記の法務 [要確認] が片付いてから着手する。
- 論点 0003 の「別途インストール or 同梱」という未確定表現を本 論点 で解消する。
