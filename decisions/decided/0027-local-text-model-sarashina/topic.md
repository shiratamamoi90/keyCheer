# 論点 0027: ローカルのテキスト生成モデルを gemma2:2b から Sarashina に変えるか

- **種別: 非決定的**
- **状態: 決定済み**
- **反映先: —**(決めた値はモデル名で、既定値の変更・移行・取得物は論点 0028〜0030 が `docs/` に反映する)

## 何を決めるか

`local-ollama` の既定モデル(`system.ollamaModel`、現行 `gemma2:2b`)を、SB Intuitions の
日本語モデル **Sarashina** 系に置き換えるか。置き換えるならどのサイズか。

**どのモデルが良いかは、日本語の応援文の質・形式の守られ方・CPU でのレイテンシといった指標でしか
決まらない**ので非決定的(@.claude/rules/experiment-rules.md)。1 論点 = 1 変数で、振るのは
**モデルだけ**。プロンプト・温度・シード・構造化出力は固定する。

背景:疎通確認では gemma2:2b から英語+絵文字の応答が返る事例があった(論点 0024 / 0021)。
日本語特化のモデルなら日本語率と文言の自然さが上がる、というのが仮説。

**指示追従(instruct)版で、CPU で回る小型のものだけ**を候補にする。

## 測り方

- 評価データ:論点 0026 と同じ。24 バケット × キャラ 3 種(性格の異なる固定プロフィール)×
  各 5 回生成。プロンプトは現行の `buildSystemPrompt` で固定。
- 固定する条件:temperature 0.8 / seed 42 / 構造化出力あり(論点 0024 の層 1。全案で揃える)/
  同じ Ollama イメージ(compose.yaml の digest)/ CPU プロファイル。
- 見る指標:
  1. **日本語率**:応答のうち日本語の文の割合
  2. **失敗バケット率**:形式違反やタイムアウトで `failed` になったバケットの割合
  3. **書式混入率**:層 3 で記号を落とす前の時点で、記号が混じっていた要素の割合
  4. **平均レイテンシ**(ms / バケット、CPU)
  5. 文言の質(人手による評価。論点 0021 の評価軸を使う)
- **主指標は日本語率**(人間の判断、2026-10-25)。ほかは副指標。
- 計測ドライバ → 実装済み(`npm run eval -- <論点フォルダ>`)。

## 中止条件

- 失敗バケット率か平均レイテンシが baseline より明らかに悪化したら、その案は打ち切って
  `却下した案` に残し、gemma2:2b のままにする。
- 候補のどれにも、出所を確認できる GGUF が見つからない場合も中止する(下の「確認事項」)。

## GGUF の出所の調査(2026-10-25。取得元の信用度で比べる)

公式(SB Intuitions)の GGUF は無く、Ollama 公式ライブラリにも Sarashina は見つからない。

| 取得元 | 誰か | 実績・検証できること | 変換の記録 | 信用度 |
|---|---|---|---|---|
| (b) 自前変換 | 公式の `sbintuitions/sarashina2.2-3b-instruct-v0.1`(safetensors、MIT)を **Ollama で直接取り込む**(Modelfile の `FROM <重みのディレクトリ>` → `ollama create --quantize q4_K_M`) | 信用するのは**公式 repo と、compose.yaml で digest を固定済みの Ollama だけ**。手順も入力のハッシュもこちらで記録できる | 自分で残せる | **高** |
| (a-1) mmnga | 個人(HF PRO)。所属 org は Algomatic Inc / MLX Community。公開モデル 301・フォロワー 308。日本語モデルの GGUF 変換を長く続けている | 先月の DL 3,956、いいね 9。量子化は IQ1_S〜Q8_0。imatrix は `TFMC/imatrix-dataset-for-japanese-llm` | llama.cpp のバージョンは書かれていない | 中 |
| (a-2) neody | 非営利の org「Neodyland」(メンバー 4、フォロワー 10 程度)。公開モデル 42 | 量子化は Q2_K〜BF16。imatrix は自前データセット(fineweb-edu / fineweb-2 から各 125 件) | README は 679 バイトで、変換の方法も llama.cpp のバージョンも無い | 低〜中 |

補足:

- GGUF は pickle と違ってコード実行を含まない**データ形式**。それでも審査が要るのは、
  (1) 中身が公式の重みと同じだと**第三者の変換物では確かめられない**、
  (2) GGUF のメタデータにはチャットテンプレート(Jinja)が入っていて、出力の形に効く、
  (3) 過去に llama.cpp の GGUF パーサーに脆弱性があった、の 3 点のため。
- (b) の手段:Ollama は safetensors の取り込みと量子化(`--quantize`、q4_K_M / q4_K_S / q8_0)を
  自前で持つ。llama.cpp の `convert_hf_to_gguf.py` は、Ollama が取り込めない場合の代替に留める。
  Sarashina2.2 は llama アーキテクチャ(mmnga の GGUF のメタデータ)で、Ollama の取り込み対象に入る。
  **実機で確認済み(2026-10-25、Ollama 0.32.13 = compose.yaml の digest)**:
  - 入力:`sbintuitions/sarashina2.2-3b-instruct-v0.1` のコミット `4f3626fb1b64b3e97c908e67f27b2d627ba2a999`。
    safetensors 2 本と `tokenizer.model` の sha256 が、Hugging Face の LFS ハッシュと一致した。
  - **BF16 のまま `ollama create --quantize q4_K_M` が通る。** 出力は Q4_K_M・3.4B・2.1 GB・context 8192
    (GGUF の層 `sha256:60e33bab403b69d923fef2bbbaf798adf1ba47cd897dfdf815bf85f433b6b959`)。
  - **チャットテンプレートは自動では当たらない**(`TEMPLATE {{ .Prompt }}` になる)。
    公式の `tokenizer_config.json` の形式(`<|system|>…</s><|user|>…</s><|assistant|>`)を Modelfile の
    `TEMPLATE` に書き、`PARAMETER stop "</s>"` / `"<|user|>"` を足す必要がある。
  - 疎通:アプリと同じリクエスト(`/api/generate` + `format` の応答スキーマ + seed 42)で 1 バケット生成すると、
    日本語の 8 文がスキーマどおりに返った。**これは疎通の確認であって計測ではない**(`result.md` には書かない)。
- (b) の代償:入力の重み(BF16 で約 6.7 GB)のダウンロードが要る。また、配布時には
  **変換した GGUF を自分たちでホストする**ことになる(論点 0010 の後続論点で扱う。MIT なので
  再配布はできる)。
- (a) を選ぶなら、コミットのハッシュとファイルの sha256 で固定する。(a) の中では mmnga が上。

**人間の判断(2026-10-25):(b) 自前変換を採る。** 公式の重みを Ollama で直接取り込み、量子化する。
入力の重みは Hugging Face のコミットのハッシュで固定し、できた GGUF の sha256 を `result.md` の
再現条件に残す。コミュニティの GGUF(mmnga / neody)は使わない。

## 人間の方針(2026-10-25)

**案B(sarashina2.2-3b-instruct-v0.1)で考える。** 計測は baseline(gemma2:2b)と案B の 2 つで行う。
案C(1b)は、案B が中止条件(レイテンシ・失敗バケット率の悪化)に掛かったときの次の候補として残す。
これは計測対象の絞り込みであって**採用の決定ではない**(決めるのは計測後。/decide)。

続けて決めたこと(2026-10-25):

- **主指標は日本語率。** 失敗バケット率・書式混入率・レイテンシ・文言の質は副指標。
- **順序:本論点を先に決める。** 論点 0021 / 0026 は、ここで選んだモデルで測り直す(同時に測らない)。

## 現在の考え

計測済み(2026-10-25、`result.md`)。案B が主指標・副指標のすべてで baseline を上回り、中止条件にも
掛からない。**案B を採用した(2026-10-25 承認)**。文言の質(人手評価)と指標関数の単体テストは未実施。

## 決定

**案B を採る。ローカルのテキスト生成モデルを `sarashina2.2-3b-instruct-v0.1` にする。**

- 重みは公式の `sbintuitions/sarashina2.2-3b-instruct-v0.1`(コミット `4f3626fb1b64b3e97c908e67f27b2d627ba2a999`)を
  Ollama で取り込み、`--quantize q4_K_M` で量子化する。コミュニティの GGUF は使わない。
- Modelfile に公式形式の `TEMPLATE` と stop(`</s>` / `<|user|>`)を書く(値は `config.yaml`)。
- 論点 0021 / 0026 はこのモデルで測り直す。

## 理由

- 主指標の日本語率が baseline の 86.1% から 90.7% に上がった。副指標(失敗バケット率 4.4% → 0.8%、
  書式混入率 6.5% → 3.7%、件数充足率 67.4% → 96.7%、レイテンシ 7.5 秒 → 6.1 秒)もすべて改善し、
  中止条件に掛からない(`result.md`)。
- 人手でサンプルを見ても(2026-10-25)、キャラの演じ分けと時間帯の反映が gemma2:2b より良い。
  gemma2:2b にはバケットキー `{normal_milestone_night}` を写した文や絵文字の混入があった。
- 取得元は信用度で選んだ。公式の重みと、digest を固定した Ollama だけを信用すれば済む
  (上の「GGUF の出所の調査」)。

## 却下した案

- **案A(gemma2:2b のまま)** — 全指標で案B を下回った。件数を守らない(8 件の要求に平均 5.4 件)。
- **案C(sarashina2.2-1b-instruct)** — 測っていない。案B が中止条件に掛からなかったので次の候補に
  進む必要が無かった。より軽いモデルが要るとき(iGPU/CPU で遅すぎる等)の候補として残る。
- **コミュニティの GGUF(mmnga / neody)** — 中身が公式の重みと同じか確かめられない。
- **llama.cpp で変換する案** — Ollama だけで取り込み・量子化できるので、依存を増やす理由が無い。
