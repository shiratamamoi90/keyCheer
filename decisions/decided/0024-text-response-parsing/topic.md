# 論点 0024: テキスト生成応答を N 文のプールに落とすパース契約

- **種別: 決定的**
- **状態: 決定済み**
- **反映先: `docs/integrations.md`(「テキスト応答のパース契約」S0024_01〜13。S0016_19 の分割規則を置き換え)**

## 何を決めるか

LLM が返した**生の応答文字列**を、プールに入る「1 文 30 字以内 × N 文」へ落とす規則。

現行の実装は行頭の箇条書き記号(`1.` `-` `*` `・`)だけを落とし、空行を捨てて上から N 件取る。
**実際の gemma2:2b 出力に対してこれが破綻することを実測で確認した**(論点 0023 で
Docker 環境を立てた際の疎通確認)。

実際の応答:

```
## チアちゃんによるキーボード打つ人を応援メッセージ

1. **キーボード勢いあふれるよ!** (normal)
2. **頑張るぞ!力いっぱい打つで!** (normal)
...
8. **キーボードの音が最高だ!** (fast)
```

現行規則を当てるとこうなる。

1. **`##` の見出し行が 1 文目としてプールに入る**(30 字に切り詰められて保存される)。
   `stripBullet` は `#` を落とさない。
2. `**` と末尾の `(normal)` が本文に残る。
3. `sanitizeMessages` の `.slice(0, 8)` が「見出し + 先頭 7 件」を取り、**8 文目が捨てられる**。

これは**応援発動時に利用者へ表示され、wav にも合成される**ため、体験に直接出る。

### 決定的/非決定的の境界(混ぜない)

- **本論点(決定的)**:与えられた応答文字列 → N 文の配列。同じ入力なら同じ出力で、
  受け入れ条件を書ける(@.claude/rules/doc-rules.md「混在する処理は境界で分割する」)。
- **論点 0021(非決定的)**:モデルが**そもそも何を返すか**(日本語で返るか・文言の質)。
  疎通確認では英語+絵文字が返る事例も観測しており、そちらはプロンプトの問題で指標でしか測れない。
- **論点 0026(非決定的)**:プロンプトに「Markdown・番号・注記を使わない」と指示して、
  **文字列の中に強調などが混ざる率が下がるか**。指示の文言を入れるかどうかは計測で決める。
- **本論点でプロンプトの文言(応援の中身・書式の指示)を触らない。** 例外は構造化出力に
  付随する「JSON で返す」という形式の指定だけで、これは下の案B の呼び出し契約に含まれる。

## 併せて決める:パース規則の置き場(共通化)

`stripBullet` は現在 **3 箇所に同じものが重複**している。

| ファイル | 状態 |
| --- | --- |
| `src/agent/providers/localOllama.ts` | 独自に定義 |
| `src/agent/providers/openaiText.ts` | 独自に定義 |
| `src/agent/providers/anthropicText.ts` | 独自に定義 |

同じ知識の**3 箇所目**は設計が共通化を要求している合図で、その見直しは判断なので論点に含める
(@.claude/rules/impl-rules.md「共通化」/ @.claude/rules/decision-rules.md)。
**3 プロバイダーとも同じ破綻をする**ので、片方だけ直す選択肢は取れない。
寄せ先は依存方向で決まる(core は I/O を持たないので、パース自体は決定的 = core 側に置ける)。

## 案

| | 案A: 行クリーニングを強化 | 案B: 構造化出力を要求 | 案C: 行のふるい分け |
| --- | --- | --- | --- |
| やり方 | 見出し `#`・強調 `**`・末尾注記 `(...)` も落とす | Ollama `format` / OpenAI JSON mode で配列を返させる | 応援文らしい行だけ採る(字数・記号率などで判定) |
| モデル差への頑健性 | 記号の種類を列挙する分だけ弱い | 強い(形式をモデルに強制) | 中(閾値の調整が要る) |
| プロバイダー横断 | 3 実装で同じ規則を共有すれば可 | **プロバイダーごとに対応状況が違う**(Anthropic は tool use、Ollama は `format`) | 可 |
| 決定性 | 高い(純粋な文字列変換) | パース自体は高い。ただし形式違反時の退避規則が別に要る | 閾値次第で境界が曖昧になりうる |
| 見出し混入の解決 | 規則に含めれば解決 | 構造上そもそも混ざらない | 字数・記号率で落とせる |
| 件数不足への対応 | 別途決める | 同左 | 同左 |
| 実装量 | 小 | 中〜大(3 実装 + 退避経路) | 中 |

## 人間の方針(2026-10-24)

**「Markdown の強調をそもそも生成させない」方向で進める。** 手段は次の 3 層に分け、
決定的な 2 層を本論点で、非決定的な 1 層を論点 0026 で決める。

| 層 | 中身 | 種別 | 置き場 |
| --- | --- | --- | --- |
| 1. 構造 | 案B:応答を「文字列の配列」として返させる。見出し行・番号・箇条書きは**構造上入らない** | 決定的(呼び出し契約) | 本論点 |
| 2. 指示 | プロンプトに書式の禁止を足す。**守られるかはモデル次第で保証できない** | 非決定的 | 論点 0026 |
| 3. 保険 | 配列の各要素から、残った強調記号(`**` 等)だけを落とす | 決定的(純粋な文字列変換) | 本論点 |

層 3 を残すのは、層 1 は**形**しか縛れず(JSON schema の制約付きデコードでも文字列の中身は自由)、
層 2 は**保証にならない**ため。プールの文は表示され wav にも合成されるので、決定的に守れる
最後の線が要る。案A は「全記号を列挙して剥がす」主役から、層 3 の「保険」へ役割を縮める。

## 決めるべき細目

1. **件数が足りないときの扱い。** 現行は「少ない分は切り上げない」(`sanitizeMessages` のコメント)。
   見出し混入で 1 件失っていた分が解消すると 8 件揃うが、モデルが 6 件しか返さない場合の
   契約は未定義。バケットを `complete` とするか `failed` とするか。
2. **切り詰めか棄却か。** 30 字超は現行「切り詰め」。文の途中で切れた文言が表示・合成される。
   棄却(その文を捨てる)に変えるかは別の判断。
3. **空バケット判定との関係。** 全文が空なら `failed`(現行)。ふるい分けを強めるほど
   `failed` が増える方向に働く。
4. **構造化出力の形式違反時の扱い。** JSON として読めない・配列でない・要素が文字列でない応答を、
   そのバケットの `failed` とするか、行分割に退避するか。退避すると層 1 の効果が消えるので
   `failed` が素直。**別プロバイダーへは自動で切り替えない**(論点 0016)のはどちらでも同じ。
   → **人間の判断(2026-10-24):プロバイダーの保証の有無で分ける。** スキーマへの準拠を保証する手段
   (Ollama `format` / OpenAI strict `json_schema` / Anthropic tool use)を使う実装では、違反を
   そのバケットの `failed` とする(保証があるのに違反した = 打ち切り等の異常で、行分割に退避すると
   層 1 の効果が消える)。保証の無い手段しか持たないプロバイダーを今後足す場合に限り、その実装は
   行分割に退避してよい。現行の 3 実装はすべて保証のある手段を持つので、**現時点では全実装 `failed`**。
5. **プロバイダーごとの構造化の手段。** Ollama は `format`(JSON schema)、OpenAI は
   `response_format`(JSON schema)、Anthropic は tool use(入力スキーマ)。
   手段は違っても**返す型(文字列の配列)と違反時の扱いは共通**にし、差は各実装の中に閉じ込める。
6. **層 3 で落とす記号の範囲。** 強調(`**` / `__`)だけか、見出し `#`・末尾注記 `(normal)` まで含めるか。
   層 1 で見出し行は入らなくなるが、要素の先頭に `#` や末尾に注記が付く余地は残る。
   → **人間の判断(2026-10-24):すべて含める。** 強調(`**` / `__`)・要素先頭の見出し記号 `#`・
   末尾の括弧注記(`(normal)` 等)を落とす。
7. **パース規則の置き場。** 3 実装に重複する `stripBullet` を core の純粋関数 1 つへ寄せる
   (上の「併せて決める」)。層 3 も同じ関数に入れる。

## 現在の考え

決定済み(2026-10-24 承認)。プロンプトの書式指示は論点 0026(非決定的)が計測で決める。

## 決定

**案B(構造化出力)を採り、層 3(記号を落とす保険)を併用する。**

1. テキスト生成の 3 実装は、応答を**共通スキーマ `{ messages: string[] }`** で返させる。手段は
   プロバイダーごとに違う(Ollama `format` / OpenAI `response_format` の strict `json_schema` /
   Anthropic の tool use + `tool_choice` で当該ツールを強制)が、返す型は共通。
2. 各要素から**強調(`**` / `__`)・先頭の見出し記号 `#`・行頭の番号や箇条書き記号・末尾の丸括弧の注記**を
   落とし、そのうえで現行の契約(30 字切り詰め・N 件で打ち切り・全文空なら `failed`)に通す。
   記号を落とすのは文字数契約の**前**。
3. スキーマ準拠を保証する手段での**形式違反はそのバケットの `failed`**。行分割に退避しない。
   保証の無い手段しか持たないプロバイダーを今後足す場合に限り、その実装は行分割に退避してよい。
4. パース規則は core の**純粋関数 1 つ**に寄せ、3 実装の `stripBullet` 重複を解消する。
5. 細目 1〜3(件数不足 / 切り詰めか棄却か / 空バケット判定)は現行の挙動を変えない。

## 理由

- 人間の方針「強調をそもそも生成させない」に対し、**決定的に守れるのは形(層 1)と後処理(層 3)だけ**。
  指示(層 2)はモデル次第なので論点 0026 で測る。層 1 は見出し行・番号の混入と「見出し + 先頭 7 件で
  8 文目が落ちる」破綻を構造で消し、層 3 は文字列の中に残る記号を落とす。
- 共通スキーマを `string[]` ではなくオブジェクトにするのは、OpenAI strict `json_schema` と Anthropic の
  tool 入力がトップレベルにオブジェクトを要求するため。3 実装で同じ形にすれば層 3 も 1 つで済む。
- 形式違反を `failed` にするのは、保証のある手段で違反した時点で打ち切り等の異常であり、行分割に
  退避すると層 1 を入れた意味が消えるため(人間の判断)。`failed` は既存の再開経路でやり直せる。
- 記号を文字数契約より先に落とすのは、`**` の 4 文字で本文が削られるのを防ぐため。
- パース規則を core に置くのは、決定的な文字列変換で I/O を持たず、3 実装が同じ知識を持つため
  (3 箇所目の重複は設計が共通化を要求している合図。@.claude/rules/impl-rules.md「共通化」)。

## 却下した案

- **案A 単独(記号を列挙して剥がすだけ)** — 見出し行の混入と件数の食い違いを形で防げず、記号の列挙は
  モデルが変わるたびに漏れる。層 3 の保険として役割を縮めて採った。
- **案C(行のふるい分け)** — 層 1 で見出し行が入らなくなれば不要。閾値の調整が境界を曖昧にする。
- **形式違反時に行分割へ退避する案** — 層 1 の効果が消える(人間の判断で不採用。保証の無い
  プロバイダーに限っては許す)。
- **プロンプト指示だけで生成させない案** — 保証にならない。論点 0026 で効果を測る対象として切り出した。

## 決まらなかったこと(次の論点へ)

- なし。細目 1〜3 は現行維持で、変えるなら新しい論点を開く。プロンプトの書式指示は論点 0026 で開済み。
